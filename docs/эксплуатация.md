# Эксплуатация Док.Москва (VDS Hostland)

Регламент для Ubuntu 24.04 LTS на VDS: установка с нуля, обновление,
ночные бэкапы, восстановление и действия при аварии (пакет W-07).

Предполагается репозиторий в `/srv/dok`, DNS:

| Имя | Тип | Значение |
|-----|-----|----------|
| `dok.moscow` | A | IP VDS |
| `www.dok.moscow` | A | IP VDS |
| `app.dok.moscow` | A | IP VDS |

Секреты только в `deploy/.env` (в git не попадает).

---

## 1. Установка с нуля (≈ 1 час)

### 1.1. Заказ VDS

- Hostland: 2 vCPU / 4 ГБ RAM / 40 ГБ NVMe, Ubuntu 24.04 LTS, доступ root по SSH.
- Запомните IP; откройте SSH-ключ (предпочтительно) или временный пароль root.

### 1.2. Базовая настройка сервера

С ноутбука:

```bash
scp deploy/server_init.sh root@IP_VDS:/tmp/
ssh root@IP_VDS 'bash /tmp/server_init.sh'
```

Скрипт идемпотентен: ставит Docker Engine + Compose plugin, ufw (22/80/443),
fail2ban (sshd), unattended-upgrades, каталоги `/srv/dok` и `/var/backups/dok`,
cron бэкапа в 03:30 UTC.

### 1.3. Клон и секреты

```bash
ssh root@IP_VDS
git clone <URL_РЕПОЗИТОРИЯ> /srv/dok
cd /srv/dok
cp deploy/.env.example deploy/.env
nano deploy/.env   # POSTGRES_PASSWORD, SECRET_KEY, BOOTSTRAP_ADMIN_*, DADATA_KEY
chmod 600 deploy/.env
```

Рекомендация для секретов:

```bash
openssl rand -hex 32   # SECRET_KEY и POSTGRES_PASSWORD
```

### 1.4. Первый запуск

```bash
cd /srv/dok
chmod +x deploy/*.sh web/docker-entrypoint.sh
./deploy/deploy.sh
```

Что происходит: `git pull` → `docker compose build app gotenberg` → `up -d`
(caddy, app, postgres, gotenberg с fonts-liberation). Entrypoint приложения ждёт БД и
выполняет `alembic upgrade head`, затем поднимает uvicorn.

Схема БД на проде и в docker — **только Alembic**. Приложение не вызывает
`Base.metadata.create_all` при старте (T1). Флаг `DB_AUTO_CREATE=true` допустим
лишь для локального sqlite без миграций; в `deploy/.env` его не задавать.

На проде в `deploy/.env` обязательно: сильный `SECRET_KEY`, `SESSION_HTTPS_ONLY=true`,
и при Яндекс ID — `YANDEX_REDIRECT_URI=https://app.dok.moscow/auth/yandex/callback`
(тот же URI в кабинете Яндекс OAuth).

Проверки:

```bash
cd /srv/dok/deploy
docker compose --env-file .env ps
curl -fsS https://app.dok.moscow/login | head
```

Войдите учёткой `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD`,
смените пароль администратора.

### 1.5. HTTPS

Caddy получает сертификаты Let’s Encrypt автоматически после корректных A-записей.
Ожидаемый рейтинг SSL Labs — A (HSTS, скрытый Server, nosniff, DENY frame).

Проверка: https://www.ssllabs.com/ssltest/analyze.html?d=app.dok.moscow

### 1.6. Мониторинг

Зарегистрируйте URL `https://app.dok.moscow/login` в
[UptimeRobot](https://uptimerobot.com/) или self-hosted Uptime Kuma
с интервалом 5 минут и уведомлением на телефон (SMS/Telegram/push).
При 5xx или таймауте — см. раздел «Авария».

## 2. Обновление приложения (канонический путь)

Единственный штатный способ обновить прод — `deploy/deploy.sh` на VDS.
Правки через `scp` отдельных `.py` **не** являются релизом (W-46).

### 2.1. Пока образ из GHCR не включён (`DOK_IMAGE` пуст)

```bash
ssh deploy@VDS
cd /srv/dok
./deploy/deploy.sh
```

Скрипт: `git pull --ff-only` → seed `core/Шаблоны` → `data/templates/system/`
→ `docker compose build` → `up -d` → smoke `/healthz` → prune образов старше 168h.
Миграции Alembic — в entrypoint `app`. Данные: `/srv/dok/data/{files,templates,ops}`.

### 2.2. Релиз по тегу (цель W-46 §2)

После CI-сборки в GHCR (`ghcr.io/<owner>/dok-app`):

```bash
cd /srv/dok/deploy
# один раз: docker login ghcr.io  (PAT read:packages)
./deploy.sh --tag vX.Y.Z
# откат:
./deploy.sh --rollback
```

Версия видна в `/healthz` и `/admin/status` (`APP_VERSION`).

Откат при сбое без тегов: предыдущий рабочий коммит + `./deploy/deploy.sh`,
либо ночной бэкап (раздел 4).

## 3. Бэкапы

### Расписание

Cron (ставит `server_init.sh`):

```text
30 3 * * * /srv/dok/deploy/backup.sh >> /var/log/dok-backup.log 2>&1
```

### Содержимое

`deploy/backup.sh` создаёт архив:

1. `pg_dump` (custom format) БД `dok`;
2. `tar.gz` каталога `/srv/dok/data/files` (W-46: host-путь == контейнер),
   без `*/imports/` и `*/exports/` (W-49: временные файлы с TTL 24 ч);
3. опционально шифрование `age` при заданном `AGE_RECIPIENT`;
4. опционально выгрузка на `BACKUP_REMOTE` (`scp` или `s3://` через aws cli);
5. ротация: 30 ежедневных в `$BACKUP_DIR/daily`, 12 месячных в `$BACKUP_DIR/monthly`.

Ручной запуск:

```bash
/srv/dok/deploy/backup.sh
ls -lh /var/backups/dok/daily/
```

Ключ `age` храните вне VDS (менеджер паролей / второй носитель). Без ключа
зашифрованный архив не восстановить.

На проде в `deploy/.env` задайте `BACKUP_REQUIRE_AGE=1` и `AGE_RECIPIENT=…`
(W-09): скрипт не сохранит открытый бэкап. Альтернатива — `GPG_RECIPIENT`.

Ежедневно в 04:15 UTC (cron `purge_retention.sh`) удаляются файлы документов
старше срока хранения организации (настройка «Безопасность» в кабинете,
по умолчанию 1095 дней).

## 4. Восстановление (`restore.sh`)

На целевом сервере уже должны быть Docker, клон репозитория и заполненный
`deploy/.env` (те же `POSTGRES_PASSWORD` / `SECRET_KEY`, что нужны для работы;
пароль БД должен совпадать с тем, под которым создавался дамп, либо вы
осознанно поднимаете новый инстанс с паролем из текущего `.env` и
восстанавливаете только данные).

```bash
# обычный архив
./deploy/restore.sh /var/backups/dok/daily/dok_2026-07-31.tar

# зашифрованный
AGE_IDENTITY=/root/.age/key.txt \
  ./deploy/restore.sh /var/backups/dok/daily/dok_2026-07-31.tar.age
```

Скрипт: распаковка → подъём postgres → `DROP SCHEMA public` + `pg_restore` →
восстановление файлов в том `files` → `compose up -d`.

Проверка: вход в кабинет, открытие журнала, скачивание свежего документа.

Восстановление **разрушает** текущую БД на целевом инстансе. Перед прогоном
на «живом» сервере сделайте свежий бэкап.

## 5. Чек-лист аварии

| Симптом | Действия |
|---------|----------|
| Сайт недоступен, мониторинг алерт | `ssh root@IP`; `cd /srv/dok/deploy && docker compose --env-file .env ps` |
| Контейнер `app` Restarting | `docker compose --env-file .env logs --tail=200 app`; проверить `.env`, место на диске (`df -h`) |
| PostgreSQL unhealthy | `docker compose --env-file .env logs postgres`; при порче данных — restore из последнего daily |
| Caddy / сертификат | проверить DNS A; `docker compose --env-file .env logs caddy`; при смене IP — обновить A-записи |
| Диск заполнен | почистить старые образы `docker system prune`; проверить ротацию бэкапов; расширить том у хостера |
| Подозрение на компрометацию | сменить `SECRET_KEY` и пароли; `ufw status`; fail2ban; восстановить из бэкапа **до** инцидента на чистый VDS |
| Нужна копия на новом VDS | `server_init.sh` → клон → `.env` → скопировать архив бэкапа → `restore.sh` → `deploy.sh` |

Контакты эскалации и доступы к DNS/хостеру храните вне репозитория.

Письма в спам / Gmail блокирует: см. `docs/почта_spf_dkim_dmarc.md` (SPF/DKIM/DMARC,
`SMTP_FROM` на своём домене). Алерты вебхука: security vs operational —
`docs/инцидент_вебхук_2026-08-08.md`.

## 7. Prune образов {#prune}

После успешного smoke `/healthz` `deploy.sh` (W-50 A.1):

1. пишет в `data/ops/deploy.log` строку
   `<ISO> tag=<tag> sha=<sha> status=ok|fail df=<pcent>`;
2. оставляет локально **два** тега `ghcr.io/…/dok-app`: текущий и
   предыдущий `status=ok` (для `--rollback`);
3. если в логе ещё нет двух `status=ok` (первый прогон нового формата) —
   PREV берётся из тега **работающего** app *до* `compose up`
   (`PRE_DEPLOY_TAG` / `running_app_image_tag`);
4. снимает остальные теги этого образа и делает `docker image prune -f`
   (postgres / caddy / gotenberg не трогает).

Разовая чистка (если диск уже > 35 % до выкладки патча):

```bash
df -h /
docker images 'ghcr.io/sudexpertpsy-afk/dok-app'
# оставить v1.2.2 и v1.2.1, остальное снять
docker image prune -f
df -h /
```

Цель W-46/W-50: после чистки **≤ 35 %**, тренд **< 0,5 ГБ/нед**
(см. `/admin/status`).

### История диска

| Дата | df / | Примечание |

## 8. Restore drill {#restore-drill}

Маркер `backup_ok` подтверждает создание архива, не восстанавливаемость.
После раскладки W-46 (`/srv/dok/data/{files,templates,ops}`) drill обязателен.

```bash
sudo /srv/dok/deploy/restore_drill.sh
# при успехе → /srv/dok/data/ops/restore_drill.json
# {"date":"…","backup":"dok_….tar.age","pg_ok":true,"files_ok":true,"checked_by":"…"}
```

Порог в `/admin/status`: возраст drill **< 90 дней**. После зелёного drill
и не ранее **2026-09-14**: `docker volume rm dok_files` (Links=0, ~4 МБ —
гигиена W-46).

## 9. TLS {#tls}

Сертификаты — 90-дневные Let's Encrypt через Caddy; продление ~на 60-й день.
Контроль — не календарь «конец октября», а `days_left` до `notAfter`.

- Worker (`ops_daily`) каждый день меряет оба хоста (`dok.moscow`,
  `app.dok.moscow`) и пишет в маркер / metrics.
- Если с контейнера до публичного IP hairpin NAT не пускает — fallback:
  TCP на сервис `caddy:443` с SNI нужного hostname (`CADDY_PROBE_HOST`).
- Алерт при **≤ 21** дня (дедуп раз в сутки).
- Вручную в первую неделю после ожидаемого renew: `notAfter` должен
  сдвинуться (~на +90 дней). Иначе — `docker compose logs caddy` (ACME,
  порт 80, DNS).

## 10. Почта SPF/DKIM/DMARC {#почта}

Пока `SMTP_FROM` не на `@dok.moscow` с валидными DNS — инвайты и алерты
рискуют попасть в спам. Дерево решений и DNS: `docs/почта_spf_dkim_dmarc.md`.

После переключения на From @dok.moscow:

1. `/admin/status` предупреждает, если домен From ≠ `dok.moscow`;
2. кнопка **«Тест доставляемости»** шлёт письмо service_admin;
3. владелец в почтовом клиенте → «Показать оригинал» → SPF/DKIM/DMARC = PASS →
   **«Подтвердить SPF/DKIM/DMARC»** (кнопка отклонит подтверждение, пока From не
   `@dok.moscow`) → маркер `data/ops/mail_auth_ok.json` с полем `from_domain`;
4. строка зелёная только если **и** текущий From, **и** `from_domain` в маркере —
   `dok.moscow`, и маркер не старше 180 дней. Маркер после теста с gmail.com
   строку зелёной не сделает.
