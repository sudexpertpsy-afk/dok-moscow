## 0. Что такое «Шаблонер»

**Шаблонер** — продукт для экспертной организации (судебная экспертиза / УСЭ): заполнение Word-шаблонов (`.docx`) реквизитами, генерация связанных документов («комплект»), учёт номеров и журнала.

Исторически это **настольное macOS-приложение** (кодовое имя **DocFiller**, UI-бренд «Шаблонер»).  
Веб-наследник — сервис **Док.Москва** (`dok.moscow` / `app.dok.moscow`): то же ядро заполнения DOCX, но без tkinter, с PostgreSQL, кабинетом, биллингом и DaData.

| Слой | Где живёт | UI | Хранение |
|------|-----------|-----|----------|
| Desktop DocFiller | `~/Downloads/Шаблонер/…` | tkinter | YAML, JSONL, Excel, локальные папки |
| Ядро (shared) | `dok-moscow/core/docfiller_core` + `core/Шаблоны` | нет | вызывается из web |
| Веб Док.Москва | `dok-moscow/web` на VDS `/srv/dok` | FastAPI + Jinja/HTMX | PostgreSQL + том `files` |

**Инвариант:** формат плейсхолдеров в DOCX (`{{ переменная }}` / Jinja2-фильтры) и имена шаблонов в реестре комплектов **нельзя ломать** без миграции всех шаблонов.

## 2. Настольный Шаблонер (логика продукта)

### 2.1. Назначение

- Заполнить шаблон договора / акта / счёта / ПКО / письма суду и т.д.
- Собрать **комплект** (договор + связанные документы) из одних данных.
- Вести счётчики номеров, журнал генераций, реестры Excel.
- Склонять ФИО, суммы прописью, даты по-русски (фильтры Jinja2).

### 2.2. Вкладки UI (desktop)

1. **Новый комплект** — data-first: тип контрагента → договор/extras → поля → генерация.
2. **Отдельный документ** — один шаблон + опционально пакет после договора.
3. **Реестр Excel** — пакетная генерация из `Реестр*.xlsx`.

### 2.3. Ключевые модули desktop (`docfiller/`)

| Модуль | Роль |
|--------|------|
| `filler.py` | `fill_template`, разбор переменных, repair таблиц |
| `filters.py` | Jinja2: склонения, даты, числа |
| `packages.py` | Состав комплекта к договору |
| `master.py` / `master_tab.py` | Логика и UI мастера |
| `counters.py`, `journal.py` | Нумерация и журнал |
| `autocomplete.py`, `linked.py` | Подсказки из журнала; «из договора» |
| `config.py`, `paths.py` | YAML и macOS-пути (`~/Library`…) |

**Не перенесены в web-ядро как есть:** GUI, `autocomplete`/`linked` (заменены form-assist + DaData), Excel-реестр как основной сценарий.

## 3. Ядро `docfiller_core` (общее)

Путь: `core/docfiller_core/` (на сервере в контейнере — `/app/core/docfiller_core`).

| Модуль | Роль |
|--------|------|
| `filler.py` | Генерация DOCX |
| `filters.py` | Фильтры шаблонов |
| `packages.py` | Related docs / suggest_fields комплекта |
| `master.py` | `core_fields(тип)` для шага 1 мастера |
| `contracts_registry.py` | Имена файлов пакета из `contracts_registry.json` |
| `counters.py`, `journal.py` | Совместимый слой (веб хранит факты в PostgreSQL) |
| `labels.py` | Человекочитаемые подписи переменных |
| `template_manifest.py` | YAML-манифесты шаблонов (новые DOCX) |
| `template_security.py` | Ограничения загрузки org-шаблонов |
| `paths.py` | Пути; веб передаёт `TEMPLATES_DIR` явно |

Подключение из web: `ensure_core_on_path()` → `sys.path` + `CORE_PATH` / `TEMPLATES_DIR`.

### 3.1. Каталог шаблонов

```
core/Шаблоны/
├── contracts_registry.json          # ключи пакета: bill_fiz, pko, rko, payment, upd…
├── *.docx                           # системные шаблоны (~40 файлов на 2026-09)
├── *.manifest.yaml                  # метаданные части новых шаблонов
└── .deleted_templates.json          # tombstone удалённых (админка)
```

**Типы комплекта (контрагент):** Физлицо / Юрлицо / Эксперт (ГПД).  
**Связанные документы (расширенный набор):** счёт, акт, ПКО, РКО, платёжка, УПД, СФ, акт сверки, ГПД/согласие и др. — см. `packages.related_documents` и реестр.

**Переменные** — кириллические имена (`фио_клиента`, `юр_адрес_заказчика`, `номер_пко`…).  
Подписи и подсказки: `labels.py` + web `form_assist` / `refs` (ОКЕИ, НДС, КБК из QuickDoc+).

## 4. Веб-обёртка (Док.Москва) поверх ядра

```
web/app/
├── main.py                 # FastAPI, middleware хостов, роутеры
├── routers/                # HTTP
├── services/               # бизнес-логика (package_*, form_assist, dadata, billing…)
├── models.py               # SQLAlchemy
├── templates/              # Jinja2 (cabinet / admin / landing)
├── static/                 # CSS/JS (хэши при сборке Docker)
└── data/refs/              # справочники подсказок
```

### 4.1. Сценарии, эквивалентные Шаблонеру

| Desktop | Веб |
|---------|-----|
| Новый комплект | `/cabinet/package/` (wizard на диске `FILES_ROOT/_wizard`) |
| Отдельный документ | `/cabinet/documents/` |
| Картотека / подсказки | `/cabinet/counterparties/`, DaData, «Вставить в комплект» |
| Настройки реквизитов | `/cabinet/settings/` |
| Журнал | `/cabinet/journal` |
| Каталог шаблонов | `/cabinet/templates/` (org) + `/admin/templates/` (системные) |

Дополнительно к desktop: биллинг, админка, `/zakon`, party-check, 2FA, PDF через Gotenberg, мультиарендность `org_id`.

### 4.2. Поток генерации комплекта

```
GET  /cabinet/package/?counterparty_id=N   → prefill core_from_counterparty
POST /cabinet/package/step1               → тип + core
POST /cabinet/package/step2               → договор + extras
POST /cabinet/package/step3               → поля → generate_package (core.filler)
GET  /cabinet/package/done                → файлы в FILES_ROOT/{org_id}/…
```

Состояние мастера: **не cookie**, а JSON в `FILES_ROOT/_wizard/{sid}.json` (`package_wizard_store.py`).

## 5. Расположение на сервере (особенности)

### 5.1. Дерево `/srv/dok`

```
/srv/dok/                      # git working tree + runtime mounts
├── .git/
├── core/                      # bind → контейнер /app/core
│   ├── docfiller_core/
│   └── Шаблоны/               # отдельно RW поверх ro core
├── web/                       # context сборки образа dok-app
│   ├── app/                   # копируется в image при build
│   ├── alembic/
│   └── Dockerfile
├── deploy/
│   ├── compose.yml
│   ├── Caddyfile
│   ├── .env                   # секреты (chmod 600), НЕ в git
│   ├── deploy.sh
│   └── backup.sh / restore*.sh
├── docs/
├── scripts/
└── files/                     # на хосте часто почти пусто — см. §5.3
```

### 5.2. Docker Compose (`name: dok`)

| Сервис | Образ / роль | Сеть |
|--------|----------------|------|
| `caddy` | TLS :80/:443 → `app:8000` | публичный |
| `app` | uvicorn `app.main:app`, 2 workers | только expose 8000 |
| `worker` | фоновые jobs (PDF, биллинг, НПА) | внутр. |
| `ops-agent` | метрики/админ-сервер :9100 | внутр. |
| `postgres` | PostgreSQL 16, том `pgdata` | внутр. |
| `gotenberg` | DOCX→PDF (+ Liberation fonts) | внутр. |

Переменные `app` (ключевые):

| Env | Значение в контейнере |
|-----|------------------------|
| `CORE_PATH` | `/app/core` |
| `TEMPLATES_DIR` | `/app/core/Шаблоны` |
| `FILES_ROOT` | `/srv/dok/files` |
| `DB_URL` | `postgresql+psycopg://dok@postgres/dok` |
| `GOTENBERG_URL` | `http://gotenberg:3000` |
| `BILLING_WORKER` | `"0"` в app (воркер отдельный) |

### 5.3. Тома и bind-mount — критичные нюансы

```
Хост                         Контейнер app
/srv/dok/core          ──ro→ /app/core
/srv/dok/core/Шаблоны  ──rw→ /app/core/Шаблоны     # поверх ro!
Docker volume dok_files ───→ /srv/dok/files         # ИМЕНОВАННЫЙ том
```

1. **Код приложения** (`web/app/*`) попадает в контейнер только через **`docker compose build`** (`COPY app ./app`). Правка файла на хосте в `/srv/dok/web/app/…` **сама по себе не действует**, пока образ не пересобран.  
   Исключение: `core/` и `Шаблоны/` — bind, видны сразу (шаблоны — сразу; `.py` ядра — после reload/restart процесса).

2. **`/srv/dok/files` на хосте ≠ данные организаций.**  
   Compose монтирует volume `files` → `/srv/dok/files` *внутри* контейнера. На хосте каталог `/srv/dok/files` может содержать только `.ops`, а реальные org-папки лежат в  
   `/var/lib/docker/volumes/dok_files/_data/{org_id}/…`  
   плюс `_wizard/`, `legal/`.

3. **Шаблоны RW:** админка может писать в `Шаблоны` на хосте (`/srv/dok/core/Шаблоны`). Ядро `docfiller_core` при этом смонтировано read-only — безопаснее для кода, но шаблоны разделяют судьбу git working tree на сервере.

4. **Статика с хэшем:** при build `scripts/hash_static.py` → `app.<hash>.css`, `form-assist.<hash>.js`. После CSS/JS правок обязателен rebuild, иначе браузер тянет старый hash из HTML кэша шаблонов.

### 5.4. Хосты и маршрутизация

Один процесс `app`, два логических сайта (`hosting.py` / middleware):

| Host | Зона |
|------|------|
| `dok.moscow` | лендинг, `/zakon`, юрстраницы |
| `app.dok.moscow` | `/login`, `/cabinet/*`, `/admin/*`, API, webhook |

Чужой surface → 301; на app — `X-Robots-Tag: noindex`.

### 5.5. Данные организаций в `FILES_ROOT`

Типично (внутри volume):

```
{FILES_ROOT}/
├── {org_id}/           # документы, загрузки, org-шаблоны
├── _wizard/            # сессии мастера комплекта
├── legal/              # артефакты законодательства (если есть)
└── .ops/               # служебное
```

Метаданные документов, контрагенты, биллинг, пользователи — в **PostgreSQL** (том `pgdata`), не в файлах.

### 5.6. Деплой на практике

| Способ | Когда |
|--------|-------|
| `./deploy/deploy.sh` | штатно: pull + build + up |
| `scp` файлов → `docker compose build app && up -d --no-deps app` | точечные хотфиксы (часто в сессиях Cursor) |
| `--no-cache` | если слой `COPY app` закэшировался и правки «не видны» |

**Дрейф кода:** на сервере git-ветка может отставать от локального клона при ручном `scp` (файлы на диске новее `git log`). Перед анализом сверять:

```bash
# на VDS
cd /srv/dok && git log -1 --oneline
# содержимое, реально в контейнере
docker compose -f deploy/compose.yml --env-file deploy/.env exec app \
  grep admin_security /app/app/main.py
```

### 5.7. Бэкапы

- Cron / `deploy/backup.sh` → `/var/backups/dok` (см. `docs/эксплуатация.md`).
- В бэкап входят БД и файловый том; секреты — только из `deploy/.env` (хранить отдельно).

## 8. Чеклист для последующего анализа

1. **Какой артефакт смотрим?** Desktop zip / `Downloads/Шаблонер` vs `dok-moscow` vs живой `/srv/dok`.
2. **Шаблон vs код:** правка DOCX — bind `Шаблоны`; правка Python web — нужен rebuild image.
3. **Файлы org:** смотреть volume `dok_files`, не пустой хостовый `/srv/dok/files`.
4. **Комплект:** состояние в `_wizard`, не в session cookie.
5. **Реестр пакета:** `contracts_registry.json` + `packages.py` + defaults НДС/refs.
6. **Синхрон git:** сравнить `git log` на VDS с локальным; scp-хотфиксы могли обогнать remote.
7. **Два хоста:** воспроизводить баг на правильном Host (`app.` vs apex).
8. **Статика:** после CSS/JS — hard refresh (новый hash в манифесте).
