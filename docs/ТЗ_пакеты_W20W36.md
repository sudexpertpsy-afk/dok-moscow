## W-34. Раздел «Сервер» в админке владельца (ops-agent)

Принципы: НЕ менять существующие маршруты и поведение сайта; всё — новый
изолированный контур за флагом OPS_AGENT_ENABLED. Никакого произвольного
shell из веба — только белый список действий.

1. Сервис ops-agent (новый контейнер в compose, тот же Python-образ,
   отдельный процесс): слушает ТОЛЬКО внутреннюю сеть compose (без
   публикации порта), авторизация по секрету OPS_AGENT_TOKEN из .env.
   Доступы агента: docker.sock (ro-операции + restart), /srv/dok (ro),
   каталог бэкапов (ro), хостовые метрики (/proc через mounts).

2. Белый список действий агента (каждое — именованный эндпойнт, без
   параметров-команд):
   - status — CPU, RAM, диск (df), аптайм, версии, статус контейнеров
     (docker ps), возраст SSL-сертификата, дата и размер последнего бэкапа
   - logs — tail N строк журнала контейнера (app/worker/caddy/gotenberg;
     postgres — только ошибки), фильтр по уровню, без ПДн (маскирование
     как в W-06)
   - restart — перезапуск ОДНОГО контейнера из списка: app, worker,
     caddy, gotenberg (postgres — нельзя)
   - redeploy — git fetch + смена на указанный тег/main + deploy.sh
     (сборка, миграции, рестарт)
   - backup_now — внеплановый backup.sh; список бэкапов; скачать архив
     (стрим через админку)
   - cert_renew — принудительная перевыдача сертификата Caddy
   Никаких: exec, произвольных команд, чтения произвольных файлов.

3. Раздел админки «Сервер» (только service_admin):
   - дашборд status с автообновлением (HTMX, 10 с);
   - просмотр логов с фильтрами;
   - restart по контейнерам: подтверждение + ввод TOTP-кода (2FA
     обязательна для всех действий изменения);
   - «Обновить сайт» (redeploy): текущий коммит и доступные новые,
     подтверждение + TOTP; лог деплоя стримится на страницу; страница
     переживает рестарт app (поллинг статуса через ops-agent);
   - «Бэкап сейчас» + список бэкапов (дата/размер/скачать);
   - все действия — в events и отдельный ops-журнал с IP.

4. Рестарт самого app: команда ставится агенту, страница опрашивает
   АГЕНТА (он жив независимо от app) и показывает «перезапуск… готово».

5. Мостики в Hostland (нет публичного API): карточка со ссылками
   (вход в панель, оплата VDS, веб-консоль) и датой окончания
   оплаченного периода VDS (вводится вручную); за 14 и 3 дня — письмо-
   напоминание об оплате.

6. Безопасность: OPS_AGENT_TOKEN ≥ 32 байт; rate limit; отказ при
   неизвестном действии; тест — из app без токена действия недоступны;
   аудит-тест белого списка (эндпойнт-инвентарь). Порт наружу не
   открывается, фаервол не меняется.

7. Тесты + docs/сервер_из_админки.md (что можно из админки, за чем идти
   в Hostland). Коммит «W-34: ops-agent».

Оценка: 4–5 дн. Зависимости: W-32 (worker и /admin/status), deploy.sh
из W-07. Что остаётся в Hostland навсегда: оплата/продление VDS,
переустановка ОС, аварийная веб-консоль при полном отказе сервера.

## W-35. «Законодательство» внутри кабинета + функции подписчика

Принципы: публичный /zakon НЕ меняется (SEO, canonical, структура — как
есть). Кабинетная версия — отдельные маршруты /cabinet/zakon/* в макете
кабинета, использующие ТЕ ЖЕ сервисы и данные (legal_acts, act_versions,
act_fragments, search_legal). Никакого копирования логики или контента.

1. Маршруты: /cabinet/zakon/ (каталог), /cabinet/zakon/{slug},
   /cabinet/zakon/search — в layout кабинета. NAV_REGISTRY: пункт
   «Законодательство» → area=cabinet, url=/cabinet/zakon/, та же
   вкладка (внешний переход убрать). Cmd+K и «Нормативная база» у
   шаблонов ведут залогиненного в кабинетную версию, анонима — в
   публичную.

2. Функции подписчика (⭐ — только платным тарифам):
   - Закладки: на акте и на статье; «Мои закладки» вверху каталога;
   - ⭐ Заметки к статье (личные, видит только автор);
   - Копировать цитату: «ст. 79 ГПК РФ (ред. от 01.06.2026) //
     Официальный интернет-портал правовой информации» — в буфер;
   - ⭐ Слежение за актом: письмо при публикации новой редакции
     (диайджест ≤ 1 письма/сутки); страница «Отслеживаемые акты»;
   - ⭐ Экспорт статьи/подборки в DOCX «Извлечение из …, редакция
     от …» через ядро;
   - История просмотров (последние 20).

3. Хранение: law_bookmarks(user_id, act_id, fragment_id NULL),
   law_notes(user_id, fragment_id, текст, обновлено),
   law_watches(user_id, act_id); всё персональное по user_id.

4. Рассылка — в задаче мониторинга W-19, только после ПУБЛИКАЦИИ
   редакции администратором.

5. Гейты: guest — базовые функции + upsell на ⭐ (механизм NAV_REGISTRY).

6. SEO: кабинетные страницы на app-хосте (noindex, W-26); публичные
   /zakon без изменений — тест: diff HTML публичных страниц пуст.

7. Тесты: паритет контента публичной/кабинетной страницы, изоляция
   заметок, письмо только после публикации, upsell, NAV-матрица.
   Коммит «W-35: законодательство в кабинете».

Оценка: 3–4 дн. Зависимости: W-22, W-26, W-28 (ссылки дашборда).

## W-36. «Единое окно»: тарифы, контент лендинга, промокоды, акции

Принципы: структура и дизайн публичных страниц неизменны — редактируется
только содержание размеченных слотов. Цены — единый источник правды
(таблица tariffs) для лендинга, кабинета и биллинга.

1. Тарифы из базы: блок тарифов лендинга и /tariffs рендерятся из
   tariffs; админка «Единое окно → Тарифы»: правка цен/описаний с
   двойным подтверждением и предупреждением «повлияет на новые оплаты»;
   tariff_price_log. Тест: цена на лендинге == цене в Init Т-Кассы.

2. Контент-слоты: content_blocks(key, заголовок, текст_markdown,
   статус, версия, обновлён, кем). Слоты: hero_заголовок,
   hero_подзаголовок, преимущества (3), тарифы_примечание, faq,
   контакты, футер_текст. Ограниченный Markdown (жирный, курсив,
   списки, ссылки), сырой HTML запрещён. Редактор с предпросмотром,
   «Опубликовать» / откат (10 версий). Fallback: пустой слот рендерит
   текст из шаблона.

3. Промокоды: promo_codes(код, тип процент/фикс, значение,
   применимость по тарифам/периодам, действует_с/по, лимит, активен).
   Поле «Промокод» на странице оплаты (HTMX-расчёт скидки); скидка
   в Init и в Receipt; код фиксируется в payments. Админка: CRUD,
   генератор, статистика. Один код на платёж, без суммирования.

4. Акции-баннер: announcement(текст, ссылка, где, с/по, стиль,
   активен) — полоса над шапкой, закрывается (cookie 7 дней).

5. Кэш: публикация слота/тарифа/баннера — purge кэша публичных
   страниц (W-31).

6. Права: только service_admin; публикации и цены — в events;
   изменение цены — с подтверждением TOTP.

7. Тесты: паритет цен, скидка в Init/чеке, лимиты/сроки промокодов,
   безопасность Markdown, fallback, сброс кэша, откат версий;
   diff публичного HTML при пустой content_blocks == 0.
   Коммит «W-36: единое окно».

Оценка: 5–6 дн. Зависимости: W-10/W-11 (биллинг), W-31 (кэш).
Отложено сознательно: реферальная программа (после 20–30 платящих),
A/B-тесты цен.
