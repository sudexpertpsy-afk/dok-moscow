### A.1. Prune образов — в deploy.sh, а не руками

**Причина находки.** 18 старых тегов `dok-app` × ~280 МБ = 8,7 ГБ в `/var/lib/containerd`: шаг
`docker image prune` из W-46 §2.2 в `deploy.sh` отсутствует или не срабатывает. Разовая чистка вернёт
диск к ~35 %, но без правки скрипта через два месяца релизов он снова будет за порогом.

**Требование.** В конце успешного деплоя (после smoke-проверки `/healthz` с новой версией):

```bash
IMAGE="ghcr.io/sudexpertpsy-afk/dok-app"
PREV_TAG="$(grep -E 'status=ok' "$OPS/deploy.log" | tail -n 2 | head -n 1 | sed -n 's/.*tag=\([^ ]*\).*/\1/p')"
# оставить текущий и предыдущий успешный тег (для --rollback), остальные теги dok-app снять
docker images "$IMAGE" --format '{{.Tag}}' \
  | grep -vxF -e "$TAG" -e "${PREV_TAG:-none}" -e '<none>' \
  | xargs -r -I{} docker image rm -f "$IMAGE:{}" || true
docker image prune -f >/dev/null            # безымянные слои
echo "$(date -Is) prune done: keep=$TAG,$PREV_TAG df=$(df --output=pcent / | tail -1 | tr -d ' ')" >> "$OPS/deploy.log"
```

Образы `postgres`, `caddy`, `gotenberg` не трогаются (prune без `-a`). `deploy.sh --rollback` продолжает
работать: предыдущий тег гарантированно остаётся локально. Формат строки в `deploy.log` зафиксировать:
`<ISO-дата> tag=<tag> sha=<sha> status=ok|fail df=<pcent>`.

**Разовая чистка сейчас** (владелец, до merge PR-1, чтобы снять красное): `docker images` → снять все
теги `dok-app`, кроме `v1.2.2` и `v1.2.1`; `docker image prune -f`; зафиксировать `df` до/после в
`docs/эксплуатация.md` (раздел «История диска»).

### A.2. Restore drill на раскладке W-46

Маркер `backup_ok` подтверждает, что архив создан, а не что из него поднимается система. После смены
раскладки данных (`/srv/dok/data/{files,templates,ops}` bind вместо named volume) восстановление ни разу
не проверялось.

**Процедура** (документируется в `docs/эксплуатация.md` → «Restore drill», выполняется владельцем, ~40 мин):

1. Взять вчерашний `dok_YYYY-MM-DD.tar.age`, расшифровать `backup.key` во временный каталог `/srv/dok/restore_test/`.
2. Проверить содержимое: `pgdump` присутствует; `data/files/{org_id}/…` — число файлов и хэши выборки (5 файлов) совпадают с прод; `data/templates/overrides/` и `.deleted_templates.json` присутствуют; `data/ops/` присутствует.
3. Поднять временный контейнер `postgres:16` на другом порту, `pg_restore` в него, выполнить три контрольных запроса: `count(*)` по `organizations`, `counterparties`, `documents` == прод на момент бэкапа (±записи за сутки).
4. Записать результат: `data/ops/restore_drill.json` → `{"date":"2026-09-13","backup":"dok_2026-09-12.tar.age","pg_ok":true,"files_ok":true,"checked_by":"deploy"}`.
5. Удалить временные контейнер и каталог.

`/admin/status` показывает возраст drill (порог 90 дней, F.1). В `backup.sh` — ничего не менять,
кроме A.4.

### A.5. Срок TLS — проверка, а не календарь

Сертификаты — 90-дневные Let's Encrypt через Caddy; продление автоматическое на ~60-й день. Контроль —
не «напомнить в конце октября», а измерять.

В worker — ежедневная задача `ops_daily` (одна для всех метрик F.1), в ней:

```python
import ssl, socket, datetime
def cert_days_left(host: str) -> int:
    ctx = ssl.create_default_context()
    with socket.create_connection((host, 443), timeout=10) as s, ctx.wrap_socket(s, server_hostname=host) as ss:
        not_after = ss.getpeercert()["notAfter"]          # 'Oct 30 12:00:00 2026 GMT'
    exp = datetime.datetime.strptime(not_after, "%b %d %H:%M:%S %Y %Z")
    return (exp - datetime.datetime.utcnow()).days
```

Для обоих хостов (`dok.moscow`, `app.dok.moscow`). Результат — в `ops_metrics` (F.1). Алерт по
операционному каналу при `< 21` дня (дедуп раз в сутки, как в хотфиксе алертов). Проверка вручную в
первую неделю октября: `notAfter` должен сдвинуться на январь; если нет — смотреть `docker logs caddy`
на ошибки ACME (порт 80, DNS).

### A.6. SPF / DKIM / DMARC

Открыто с 08.08, релей через Gmail. Пока это не закрыто, страдают инвайты, письма о выгрузке,
подтверждения регистрации и алерты. Действия — у владельца (DNS), в коде — только проверка и маркер.

**Дерево решений** (по `SMTP_HOST`/`SMTP_FROM` в `.env`):

1. **Google Workspace на домене dok.moscow** (ящик вида `noreply@dok.moscow` в Workspace):
   SPF `TXT @ "v=spf1 include:_spf.google.com -all"`; DKIM — Admin Console → Apps → Google Workspace →
   Gmail → Authenticate email → сгенерировать ключ 2048 → `TXT google._domainkey`; DMARC —
   `TXT _dmarc "v=DMARC1; p=none; rua=mailto:dmarc@dok.moscow; adkim=s; aspf=s"`, через две недели
   без ложных срабатываний — `p=quarantine`.
2. **Личный gmail.com с подменой From на @dok.moscow** — DKIM для домена получить нельзя, SPF не
   пройдёт. Перейти на почтовый сервер домена (у хостера/регистратора — SPF `include:` по их
   документации, DKIM в их панели) либо на российский транзакционный SMTP. Это единственный вариант,
   при котором `From: @dok.moscow` перестанет попадать в спам.

**В приложении:**
- при старте — предупреждение в лог и в `/admin/status`, если домен `SMTP_FROM` ≠ `dok.moscow`
  или отсутствует `SMTP_FROM_NAME`;
- кнопка `/admin/status` → «Тест доставляемости»: отправить письмо на адрес service_admin;
  владелец открывает «Показать оригинал» в Gmail и видит `SPF: PASS`, `DKIM: PASS`, `DMARC: PASS`,
  после чего нажимает «Подтвердить» — записывается маркер `data/ops/mail_auth_ok.json` с датой.
  Порог в чек-листе: маркер не старше 180 дней.

## B. Организации и лиды

> **Промпт для Cursor (часть B).** Модели `organizations`, `users`, `leads`, `invites`; роутеры
> `/admin/leads`, `/admin/orgs`, `/signup`, `/invite/*`. Одна миграция Alembic с `downgrade`. Не удалять
> данные миграцией — только добавлять поля. Все удаления организаций — через guard-функцию
> `can_purge_org()` и с событием. Тесты на идемпотентность, purge и политику 2FA обязательны.

### B.1. Причина «пустых» организаций

Аудит: org 7+8 и 9+10 — пары дублей с одним e-mail, созданы `lead_invite` 14.08 и 31.08, users=0,
события `invite_deleted ×2`. То есть `create_org` вызывается при **создании** инвайта, и повторный инвайт
на тот же e-mail создаёт вторую организацию. Организация без пользователя — состояние, которого не должно
существовать.

### B.2. Идемпотентный инвайт: организация — при принятии

- Создание инвайта из заявки **не создаёт** организацию. В инвайте хранятся будущие имя организации,
  тариф/промо и срок действия.
- Организация и её первый `org_admin` создаются **в одной транзакции при принятии инвайта** (форма
  пароля/Яндекс ID на `app.dok.moscow`).
- Повторный инвайт на e-mail с активным (не истёкшим, не принятым) инвайтом — **не новый инвайт**, а
  продление срока и повторная отправка письма (событие `invite.resent`). БД: частичный уникальный индекс
  `invites(lower(email)) WHERE status='active'`.
- Если для e-mail уже есть пользователь — инвайт невозможен, админке показывается организация этого
  пользователя.
- Self-serve регистрация (W-47): если сейчас организация создаётся до подтверждения e-mail — привести к
  той же схеме: до подтверждения существует только запись `signups(email, token, org_name, expires_at)`;
  организация и пользователь создаются при подтверждении. Если уже так — оставить, добавить тест.

### B.3. Purge

Guard `can_purge_org(org) -> (bool, reason)`: `users=0` **и** `documents=0` **и** `counterparties=0`
**и** нет платежей со статусом `confirmed` **и** нет активного инвайта **и** возраст > 7 дней.

- Worker (ежедневно): организации, проходящие guard, удаляются с событием `org.purged {reason:"empty",
  created_at, source:"lead_invite|signup"}` и удалением `FILES_ROOT/{org_id}` через `safe_paths`.
- `signups` старше 7 дней без подтверждения — удаляются, событие `signup.expired`.
- Админка → «Организации»: кнопка «Удалить пустую организацию» с тем же guard (для нынешних 7–10 —
  **после** того, как владелец свяжется с обоими адресами; `psy-expert.ru` похож на профильного коллегу).
  Кнопка недоступна, если guard не проходит; причина показывается.

### B.4. `is_internal`

Миграция: `organizations.is_internal boolean not null default false`. Переключатель в карточке
организации в админке (только service_admin), событие `org.internal_changed`. Владелец отмечает УСЭ,
ЦСИЭ, СОП, `psy.d.losev` по своему усмотрению.

Исключаются из всех показателей `/admin/обзор` и ежемесячного аудита (F.2): медиана онбординга,
воронка заказов, «документов за период», «активных организаций». Везде — переключатель «включая
внутренние» (по умолчанию выключен) и отдельная строка «внутренние: N». Пока из восьми организаций
четыре ваши, любой KPI без этого флага показывает вас самих.

### B.5. Политика 2FA

Сейчас 2FA — 1/8, включена только у service_admin. Данные организаций — паспорта и сведения о
здоровье; пароль не должен быть единственной защитой у тех, кто управляет организацией.

- Правило: `org_admin` организации с **платной** подпиской обязан включить TOTP в течение 7 дней с
  момента `max(дата начала платной подписки, дата включения политики)`.
- До дедлайна — баннер в кабинете с обратным отсчётом и кнопкой «Включить». После дедлайна —
  «мягкая» блокировка: маршруты «Данные организации» (выгрузка), «Сотрудники» (инвайты), «Нумерация»,
  «Тариф и оплата» требуют 2FA и перенаправляют на её настройку; документы, картотека, шаблоны
  работают. Событие `security.2fa_policy_block` при первом перенаправлении.
- `org_member` и «Гость» — только напоминание раз в 30 дней (баннер, закрываемый).
- Флаг `TWO_FA_POLICY_ENABLED` в настройках (по умолчанию включён), дата включения — в
  `settings` (для расчёта дедлайна у существующих организаций).
- `/admin/status` и аудит: доля 2FA среди `org_admin` платных организаций (порог 100 %) и среди всех
  пользователей (индикатор без порога).

### B.6. Тесты части B

Два инвайта на один e-mail → одна организация после принятия, второй инвайт = продление; принятие
инвайта создаёт org + org_admin атомарно (при падении на втором шаге — ни org, ни user); self-serve:
до подтверждения org нет, после — есть; purge: guard отказывает при документах / подтверждённом платеже /
активном инвайте / возрасте < 7 дней, удаляет при выполнении всех условий, файлы org удалены, событие
записано; IDOR: кнопка purge недоступна org_admin; `is_internal` исключает из KPI (фикстура: две
организации, одна внутренняя — медиана и воронка считаются по одной); 2FA-политика: до дедлайна —
баннер, после — редирект с четырёх маршрутов, остальные работают; отключение флага снимает всё.

## C. Биллинг: гигиена

> **Промпт для Cursor (часть C).** `billing/` (Init, GetState, webhook, reconcile), модель `orders`,
> `promo_uses`. Не менять протокол Т-Кассы (Token, Receipt, NotificationURL). Все суммы — целые копейки.
> Каждое изменение статуса заказа — событие. Тесты с моком Т-Кассы.

### C.1. Заказ создаётся только по нажатию «Оплатить»

`GET` страницы тарифа/оплаты не вызывает `Init` и не создаёт `orders`. `POST /billing/pay` (кнопка) —
единственная точка создания.

### C.2. Один открытый заказ на организацию

При `POST /billing/pay`: если есть заказ `status='created'` той же организации с тем же тарифом и
периодом, созданный < 20 минут назад, — переиспользовать его `PaymentURL` (редирект). Иначе старый
открытый заказ помечается `cancelled_by_new` (с вызовом `Cancel` в Т-Кассе для статуса `NEW`, если
реализован; при ошибке — только локальная отметка), создаётся новый.

### C.3. Истечение

Worker (внутри `billing_reconcile`): заказы `created` старше 24 ч → `GetState`; `NEW` /
`CANCELED` / `DEADLINE_EXPIRED` / `REJECTED` → `expired`; `CONFIRMED` (пропущенный вебхук) →
обычная обработка подтверждения. Заказы старше 7 дней без ответа Т-Кассы → `expired` с пометкой
`unreachable`. Всё — события `billing.order_state_changed`.

### C.4. Промокод: резерв → фиксация → освобождение

`promo_uses`: запись `reserved` при `Init`, `committed` при `confirmed`, `released` при
`expired`/`cancelled`. Лимит промокода считается по `reserved + committed`; освобождённые не считаются.
Тест: промо на 1 использование, два заказа подряд — второй получает отказ; первый истёк — второй
проходит.

### C.5. Копейки

Аудит кода: все суммы (`orders.amount`, тарифы, скидки, промо, `Receipt.Items[].Amount`/`Price`)
— `integer` в копейках; ни одного `float`/`Decimal`-деления без округления. Тест: годовая подписка со
скидкой 10 % и промо −50 % на сумме 2 700 ₽ → сумма в `Init` равна сумме в `Receipt` до копейки.

### C.6. Метрика воронки

`/admin/обзор` → «Оплата за 30 дней»: заказов создано / подтверждено / истекло / отменено, доля
истёкших; **без `is_internal`**; график по неделям. Порог чек-листа: доля истёкших < 30 %. Сейчас
35/4 — почти все свои тесты; после `is_internal` и C.1–C.3 метрика станет осмысленной.

## D. Импорт: составные поля и единый реестр полей

> **Промпт для Cursor (часть D).** Сначала D.3 (реестр), затем D.1–D.2 поверх него. Реестр — единственный
> источник канонических ключей, алиасов, синонимов заголовков и парсеров; `prefill`, импорт, DaData-маппинг и
> `upsert` обязаны читать только его. Ничего не удалять из ядра `docfiller_core`; плейсхолдеры шаблонов
> `{{ … }}` и фильтры — инвариант. Контракт-тест round-trip обязателен.

### D.1. Причина находки

У ФЛ УСЭ паспорт есть — в `реквизиты_документа` строкой «4518 569137 выдан ОВД … 12.03.2010», при
`документ_основания = «Паспорт гражданина РФ»`. Импорт ищет `паспорт_серия`/`паспорт_номер` и не
находит. Это не особенность УСЭ: у любого пользователя в Excel паспорт будет в одной ячейке, банк — в
одной ячейке «р/с … в … БИК … к/с …», ИНН/КПП — через дробь. Нужен парсер составных полей.

### D.2. Парсеры составных полей

Модуль `fields/composite.py` (в реестре D.3). Каждый парсер: вход — строка, выход — `dict` канонических
ключей + `confidence` (`full` / `partial` / `none`) + список нераспознанных фрагментов. Валидация
результатов — валидаторами ядра.

**Паспорт** (`parse_passport`):
- серия и номер: `(?<!\d)(\d{2})\s?(\d{2})\s?(\d{6})(?!\d)` → `passport_series = g1+g2`, `passport_number = g3`;
- код подразделения: `(\d{3}-\d{3})` → `passport_dept_code`;
- дата выдачи: первая дата `(\d{2})[./](\d{2})[./](\d{4})` **после** маркера «выдан»; если маркера
  нет — единственная дата в строке; две даты без маркера — `partial` и предупреждение;
- кем выдан: текст между маркером («выдан», «выд.», «выдано», «кем выдан:») и датой/кодом, без
  завершающей пунктуации; при отсутствии маркера — `partial`;
- вход, где нет 10 цифр серии-номера → `none`.

**Банковские реквизиты** (`parse_bank`):
- расчётный счёт: 20 цифр, начинающиеся на `40` (`405–408`) → `bank_account`;
- корреспондентский: 20 цифр, начинающиеся на `301` → `bank_corr`;
- БИК: 9 цифр, начинающиеся на `04` → `bank_bic` (валидатор БИК ядра);
- наименование банка: текст после «в »/«банк»/до «БИК», очищенный → `bank_name`;
- ключевание р/с по БИК (алгоритм весов 7-1-3): если в `validators.py` нет — добавить в ядро с тестами
  на 5 реальных парах (взять из собственных реквизитов УСЭ и открытых примеров ЦБ).

**ИНН/КПП** (`parse_inn_kpp`): `(\d{10})\s*/\s*(\d{9})` → `inn`, `kpp`; `\d{12}` → `inn` (ФЛ/ИП).
**ФИО + дата рождения в одной ячейке** (`parse_person_line`): ФИО до первой даты, дата → `birth_date`.

**Где применяется:**
1. Мастер импорта, шаг 1: новые цели сопоставления «Паспорт (одной строкой)», «Банковские реквизиты
   (одной строкой)», «ИНН/КПП»; синонимы заголовков: «Паспорт», «Паспортные данные», «Документ»,
   «Реквизиты», «Банк», «Банковские реквизиты», «ИНН/КПП».
2. Шаг 2 (предпросмотр): разобранные части показываются отдельными колонками; `partial` — ⚠ с
   текстом «распознаны серия и номер, не распознано: кем выдан»; строка импортируется с тем, что
   распознано, остаток — в `notes` карточки, чтобы ничего не потерять.
3. Импорт из `.journal.jsonl` (desktop): если `документ_основания` ∈ {«Паспорт гражданина РФ»,
   «Паспорт»} — `реквизиты_документа` через `parse_passport`; аналогично банковские поля контекста.
4. Ручная карточка контрагента: поле «Вставить паспорт одной строкой» с кнопкой «Разобрать» (HTMX),
   заполняющей отдельные поля — экономит ввод при переносе из письма заказчика.

**УСЭ практически:** журнал на сервере удалён по TTL (норма W-49), но он есть на машине с настольным
Шаблонером. После выкладки D — повторный импорт `.journal.jsonl` в режиме «обновить пустые поля»:
ожидаемый результат — паспорт у ~39 ФЛ, создано 0, дублей 0 (это одновременно повторная проверка
дедупликации на живых данных).

### D.3. Единый реестр полей (`docs/w49_field_alias_registry.md` → код)

Один модуль (`core/docfiller_core/fields_registry.py`, если ключи — часть ядра; иначе
`web/app/fields/registry.py` с импортом ключей ядра):

```python
FIELDS = {
  "inn": Field(aliases=["инн", "инн_заказчика", "INN"], headers=["ИНН", "инн", "INN", "ИНН заказчика"],
               validator="inn", dadata="party.data.inn", entity=["UL","FL","IP"]),
  "legal_address": Field(aliases=["юр_адрес", "адрес_заказчика", "юр_адрес_заказчика"],
               headers=["Юридический адрес","Юр. адрес","Адрес"], dadata="party.data.address.unrestricted_value"),
  "bank_bic": Field(aliases=["бик", "бик_заказчика"], headers=["БИК"], validator="bic", composite="bank"),
  "passport_series": Field(aliases=["паспорт_серия"], composite="passport"),
  ...
}
COMPOSITES = {"passport": parse_passport, "bank": parse_bank, "inn_kpp": parse_inn_kpp}
```

Потребители — **только через реестр**: `resolve(alias) -> canonical`, `aliases_of(canonical)`,
`headers_index()`, `dadata_map()`, `composite_for(key)`. Четыре места, где сейчас алиасы разрешаются
по-своему (prefill карточка→мастер, импорт, DaData в формах, upsert при генерации), переводятся на
реестр; локальные словари удаляются. Ключи счётчиков и плейсхолдеров шаблонов — из реестра ядра, как
раньше; реестр их не переопределяет, а ссылается.

**Контракт-тест round-trip** (`tests/test_fields_roundtrip.py`): заполнить карточку контрагента
уникальными маркерами во всех ключах реестра (`inn` → валидный тестовый ИНН, остальное — строки
`MARK_<key>`), прогнать: карточка → prefill мастера → генерация комплекта (фикстурный шаблон, где
каждый ключ есть плейсхолдером) → `upsert` → карточка; проверить, что каждый маркер (а) попал в
документ, (б) вернулся в карточку без изменений, (в) пустое значение с формы не затёрло непустое в
карточке. Второй тест — обратный: маркеры через импорт XLSX с заголовками из `headers` → карточка.
Эти два теста ловят весь класс ошибок «сверки связей» разом.

### D.4. Тесты части D

Парсеры: по 8–10 реальных форматов на каждый (пробелы/без, «выд.», код подразделения до/после даты,
две даты, мусор в конце; банк — порядок р/с/к/с/БИК произвольный, название банка в кавычках и без);
предпросмотр показывает `partial`; `notes` получает остаток; journal-импорт заполняет `passport_*`;
реестр: каждый алиас разрешается ровно в один канонический ключ, нет двух ключей с общим алиасом
(тест на коллизии), все плейсхолдеры системных шаблонов присутствуют в реестре (тест против
`contracts_registry.json` и манифестов); round-trip — оба направления.

## E. НПА: нормализация и объём мониторинга

> **Промпт для Cursor (часть E).** Модель `act_versions`, задача `legal_watch`, экран ревью diff в админке.
> Не менять источники (pravo.gov.ru, ИПС). Нормализация — чистая функция с тестами на фикстурах. Сначала
> прогнать нормализацию по 20 текущим draft и показать, сколько из них — только форматирование.

### E.1. Причина находки

20 draft-редакций КоАП без `reviewed_at`, diff ~2,7 МБ. Diff такого размера — не поправки, а
переформатирование источника (переносы, неразрывные пробелы, типографика, колонтитулы). Такую очередь
человек не вычитает, поэтому она растёт.

### E.2. Нормализация перед сравнением

`legal/normalize.py`: `unicodedata.normalize("NFC")`; ` `, ` ` → пробел; кавычки
`«»„“”"` → `"`; тире `– — ‑` → `-`; схлопывание пробелов и пустых строк; удаление колонтитулов и
номеров страниц (паттерны источника — вынести в конфиг по акту); мягкие переносы `­` — удалить.
Сравнение — по `sha256(normalized)`.

- Нормализованный текст **не изменился** → версия помечается `formatting_only=true`,
  `reviewed_at=now`, `reviewer='auto'`, в очередь не попадает; событие `legal.version_autoarchived`.
- Изменился → diff по статьям (E.3).

### E.3. Diff по статьям

Разбиение нормализованного текста по `^Статья\s+(\d+(?:\.\d+)*)\.` (для кодексов) или по нумерованным
разделам (для 73-ФЗ). Diff считается **по каждой статье** отдельно; в очередь ревью попадает сводка:
«КоАП, редакция от 02.09.2026: изменено 3 статьи — 26.4, 26.5, 27.10; добавлено 0; удалено 0».
Экран ревью показывает только изменённые статьи (свёрнутые остальные), с подсветкой на уровне
предложений. Размер diff в БД падает с мегабайт до килобайт.

### E.4. Объём мониторинга

Per-act настройка `watch_articles: list[str] | null` в конфиге источников. `null` — весь акт (73-ФЗ,
ГПК, УПК, АПК, КАС). Для КоАП — **предложение, согласовать с владельцем**: ст. 25.8 (специалист),
25.9 (эксперт), 26.2 (доказательства), 26.4 (экспертиза), 26.5 (пробы и образцы), 26.11 (оценка
доказательств), гл. 27 — не включать. Изменения вне списка — версия сохраняется с
`out_of_scope=true`, авто-архив, счётчик в аудите отдельной строкой. Список редактируется в админке
(«Законодательство → Источники»).

### E.5. Разбор текущей очереди

Одноразовая команда `manage.py legal_renormalize`: прогнать E.2 по всем draft → ожидание: большинство
из 20 уйдёт как `formatting_only`; остаток пересчитать по E.3 и оставить владельцу сводки. Результат —
в отчёт PR.

`/admin/status`: «НПА: ожидают ревью N, старейшая — M дней» — порог: 0 старше 14 дней.

### E.6. Тесты части E

Нормализация идемпотентна и устойчива к перестановке пробелов/кавычек/тире (фикстуры: один текст в
трёх «оформлениях» → один хэш); реальная поправка (изменено одно слово в ст. 26.4) → diff ровно по
одной статье; `watch_articles` фильтрует; авто-архив пишет событие и не создаёт задачу ревью;
`legal_renormalize` идемпотентен (повторный запуск ничего не меняет).

### F.2. Ежемесячный аудит

Worker, 1-го числа 06:00 МСК, задача `monthly_audit`:

1. Собирает все строки F.1 плюс сводку по организациям (число, из них внутренних, с платной
   подпиской, активных за 30 дн), контрагентов, документов, платежей (без имён, без e-mail, без ПДн),
   версию прода, состав контейнеров (из `docker compose ps` через ops-agent whitelist-действие
   `compose_ps`), `alembic head`.
2. Пишет `data/ops/audit/YYYY-MM.json` и `YYYY-MM.md` (тот же чек-лист в таблице, красные — сверху).
3. Отправляет Markdown письмом service_admin; показывает в `/admin/status` → вкладка «Аудиты»
   (список, просмотр, скачать).
4. Раздел «Суждения» в Markdown — пустой, для человека: аудит отвечает «что вышло за порог», решения
   пишет владелец. Кнопка «Сохранить суждения» дописывает текст в `.md` (событие).

Формат JSON фиксируется в `docs/формат_аудита_v1.md` (как для экспорта), чтобы старые аудиты можно
было сравнивать между собой; в `.md` — строка «Δ к прошлому месяцу» по каждой числовой метрике.

### F.3. Тесты части F

Пороги: для каждой строки — три фикстуры (зелёный/жёлтый/красный) → правильный цвет; тренд диска на
синтетических точках; аудит на фикстурной БД → JSON валиден по схеме, в нём нет `@`-адресов и
10/12-значных чисел вне разрешённых полей (тест на утечку ПДн); письмо отправляется один раз; повторный
запуск за тот же месяц не создаёт второй файл.
