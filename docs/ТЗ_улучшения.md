## 1. Анализ текущего состояния

### 1.1. Что сделано хорошо

- **Единый реестр навигации (NAV_REGISTRY).** Меню, поиск, sitemap и тарифные гейты строятся из одного источника правды, покрытие маршрутов проверяется тестом — это редкая дисциплина, её нужно сохранить и опереть на неё дальнейшие работы.

- **Орг-центричная изоляция.** org_scope на сущностях, файлы по FILES_ROOT/{org_id}, тарифные гейты с upsell — фундамент мультиарендности заложен корректно.

- **Связанный основной контур.** Документы ↔ комплект ↔ контрагенты ↔ журнал ↔ календарь ↔ биллинг образуют работающую петлю ценности; DaData и Т-Касса встроены в неё, а не сбоку.

- **Эксплуатационная гигиена.** Секреты в .env, статус конфигурации в админке, ROUTE_EXCEPTIONS под тестом.

## 2. Рабочие пакеты

### W-26. Разделение хостов, SEO-гигиена и перелинковка

- Host-middleware: публичные маршруты (лендинг, юр. страницы, /zakon, robots, sitemap) отдаются только на dok.moscow; кабинет, /login, /admin, /api, вебхук — только на app.dok.moscow; чужой маршрут на хосте → 301 на правильный хост. ROUTE_EXCEPTIONS дополнить полем host.

- SEO: canonical на всех публичных страницах; robots.txt по хосту (на app.dok.moscow — Disallow: / полностью); sitemap только на публичном хосте; заголовок X-Robots-Tag: noindex на всех ответах app-хоста.

- Cookie: SESSION_COOKIE_DOMAIN не задавать (кабинетная cookie — только app.dok.moscow); проверить Secure/HttpOnly/SameSite=Lax.

- Перелинковка app → публичный слой: в футере кабинета — «Нормативная база», «Оферта», «Политика ПДн», «Тарифы»; пункт «Законодательство» в NAV_REGISTRY (area=cabinet, открывается на публичном хосте в новой вкладке); блок «Нормативная база» на странице генерации документа (ссылки на релевантные /zakon/{slug} из манифеста шаблона — поле нормативная_база в манифесте).

- Перелинковка публичного слоя: из карточек /zakon — блок «Создавайте документы по этой норме в Док.Москва» (мягкий CTA на регистрацию).

Критерии приёмки: лендинг недоступен на app-хосте (301), кабинет недоступен на публичном (301 на app); проверка Яндекс.Вебмастером — нет дублей; из кабинета в 2 клика достижимы все юр. страницы и /zakon; тест host-матрицы маршрутов.

### W-27. Роли организации и раздел «Сотрудники»

- БД: поле users.org_role (org_admin / org_member); миграция: первый (старейший) пользователь организации → org_admin, остальные — org_member. NavRole связать с реальным полем.

- Гейты: «Настройки» организации (реквизиты, банк, подписи, цены, счётчики) и «Мои шаблоны» — только org_admin; org_member получает read-only просмотр реквизитов. Security-раздел (свои 2FA/пароль/Яндекс) — каждому.

- Раздел «Сотрудники» (тариф Organization, только org_admin): список пользователей организации, приглашение по e-mail в рамках лимита тарифа (та же механика invite, но от организации), деактивация сотрудника, передача роли org_admin (с подтверждением). Админка сервиса видит и может всё то же.

- События: все действия с ролями и сотрудниками — в events; письмо приглашённому и письмо org_admin при деактивации.

Критерии приёмки: org_member не может открыть настройки организации (403 + понятная страница); инвайт сверх лимита тарифа блокируется с upsell; тест-матрица прав по всем разделам кабинета; существующие организации мигрируют без потери доступа.

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-27 по docs/ТЗ_улучшения.md: поле users.org_role с миграцией (старейший пользователь org → org_admin), пересадка NavRole на реальное поле, гейты настроек организации, раздел «Сотрудники» (инвайты организации в лимите тарифа, деактивация, передача роли), события и письма. Обнови NAV_REGISTRY и тест-матрицу прав: для каждого пункта реестра — тест доступа org_admin/org_member/guest. Прогони pytest.*

### W-28. Стартовая страница кабинета и панель «Требуют внимания»

- /cabinet/ — дашборд вместо 303: приветствие; счётчики за месяц (документов создано, комплектов, лимит «Гостя» с прогрессом); блок «Требуют внимания»: договоры, истекающие ≤ 14 дней; договоры без акта; неоплаченные счета (по статусам биллинга организации-клиентов это не касается — только её собственные документы); ближайшие события календаря (5 шт.); кнопки быстрых действий (Новый комплект, Новый документ, Проверить по ИНН).

- Блок «Что нового в законодательстве»: последние 3 обновлённые редакции из /zakon (перелинковка с W-26).

- Пункт «Главная» в NAV_REGISTRY первым в сайдбаре; логотип кабинета ведёт на дашборд.

- Все выборки дашборда — одним-двумя SQL-запросами с индексами (не N+1); время ответа дашборда ≤ 300 мс на демо-данных (тест).

Критерии приёмки: вход ведёт на дашборд; каждая строка «Требуют внимания» кликабельна и ведёт к сущности; пустые состояния оформлены (новая организация видит онбординг-подсказки: «1. Заполните реквизиты → 2. Создайте первый комплект»).

### W-29. Единый поиск

- Выделить поисковую службу services/search.py (использует search_legal и сущностные под-поиски из W-23); /api/global-search и страница /cabinet/search работают через неё одну.

- /cabinet/search становится страницей результатов «показать все» для Cmd+K (та же группировка, пагинация внутри групп); дублирующую старую логику удалить.

- В Cmd+K добавить строку «Показать все результаты → /cabinet/search?q=…».

Критерии приёмки: результаты палитры и страницы идентичны (общий тест на фикстурах); старый код поиска удалён; время ответа ≤ 300 мс.

### W-30. Быстродействие: фоновая генерация и база данных

- **Асинхронный PDF.** Генерация PDF и комплектов (zip/объединённый PDF) — фоновой задачей: запрос ставит job (таблица jobs: тип, статус, payload, результат), страница показывает прогресс HTMX-поллингом (1–2 с) и отдаёт готовый файл; DOCX по-прежнему отдаётся мгновенно. Недоступный Gotenberg → понятный статус задачи и повтор, а не таймаут страницы.

- **Аудит запросов.** Включить логирование медленных SQL (\> 200 мс) в dev; пройти журнал, дашборд, картотеку, платежи на N+1 (selectinload/joinedload); пагинация везде, где список может превысить 100 строк (журнал уже постранично — проверить остальные).

- **Индексы.** Ревизия по фактическим планам (EXPLAIN): documents(org_id, создан DESC), contracts(org_id, статус, дата_окончания), counterparties(org_id, наименование trigram), payments(org_id, создан DESC), события календаря по дате; FTS-индексы /zakon подтверждены W-22.

- **Пул и воркеры.** SQLAlchemy pool_size/max_overflow под 2 vCPU; uvicorn --workers 2; фоновые задачи (биллинг-jobs, мониторинг НПА, сверка) — в одном выделенном scheduler-процессе (отдельный сервис в compose: тот же образ, команда worker), а не в каждом веб-воркере дважды.

Критерии приёмки: комплект из 5 документов с PDF не блокирует другие запросы (нагрузочный тест: 10 параллельных генераций + browsing); P95 страниц кабинета ≤ 500 мс на демо-данных ×1000 документов; jobs переживают рестарт контейнера (статусы восстанавливаются).

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-30 по docs/ТЗ_улучшения.md: таблица jobs + фоновый исполнитель в отдельном процессе (compose-сервис worker на том же образе), перевод PDF/комплектов на jobs с HTMX-прогрессом, ревизия N+1 и индексов по EXPLAIN (миграция с новыми индексами), настройка пула SQLAlchemy и uvicorn workers, перенос всех периодических задач в worker с логом запусков. Нагрузочный тест: 10 параллельных генераций комплекта + фоновые запросы страниц, P95 ≤ 500 мс. Прогони pytest.*

### W-31. Быстродействие: фронтенд и статика

- Caddy: encode zstd gzip; Cache-Control: статика с хэшем в имени (main.abc123.css) — immutable, 1 год; samples/\*.pdf — 1 день; страницы — no-store для кабинета, короткий кэш для лендинга и /zakon (public, max-age=300).

- Сборка статики: лёгкий шаг в Dockerfile — хэширование имён (manifest.json) без введения node-сборщика; Jinja-хелпер static_url().

- Изображения лендинга — WebP + width/height (без CLS); отложенная загрузка скриншотов; критический CSS лендинга инлайном (страница статична).

- HTMX-фрагменты: заголовок Vary корректен; тяжёлые списки — подгрузка по скроллу (журнал, платежи).

Критерии приёмки: PageSpeed лендинга ≥ 95 mobile; /zakon ≥ 90; повторная загрузка кабинета — статика из кэша (0 запросов к статике в waterfall); отчёт замеров до/после в docs/быстродействие.md.

### W-32. Наблюдаемость и сводный статус

- Middleware тайминга: время ответа в access-лог; страница /admin/status расширяется: P50/P95 за час по группам маршрутов, статус последних запусков фоновых задач (мониторинг НПА, сверка Т-Кассы, автопродления, бэкап), возраст последнего успешного вебхука, свободное место на диске, размер БД.

- Алерты письмом администратору: фоновая задача не выполнялась дольше 2× интервала; ошибка вебхука 3 раза подряд; диск \> 85%; неудачный ночной бэкап (интеграция с backup.sh через файл-маркер).

- Еженедельный дайджест владельцу: организации/платежи/документы за неделю, топ ошибок из лога, статус НПА-мониторинга.

Критерии приёмки: искусственная остановка worker видна на /admin/status и приходит письмом в течение часа; дайджест формируется по расписанию.

### W-33. Чистка поверхности

- Удалить заглушку /cabinet/org/{org_id} (изоляция покрыта тестами) и провести ревизию ROUTE_EXCEPTIONS — каждый маршрут либо в NAV_REGISTRY, либо с комментарием-обоснованием.

- vulture/deptry по web/: мёртвый код и неиспользуемые зависимости; удалить старую логику /cabinet/search (после W-29).

- Единые страницы ошибок 403/404/500 в стиле кабинета и лендинга (по хосту), с полезными ссылками.

Критерии приёмки: отчёт чистки в docs/; все тесты зелёные; никакой маршрут не отвечает на «чужом» хосте (совместно с W-26).

## 4. Что сознательно отложено

- Redis/очереди уровня Celery — таблица jobs в PostgreSQL достаточна до сотен генераций в час; возврат к вопросу при росте.

- CDN для статики — после появления заметного трафика; Caddy-кэша достаточно.

- Разнесение хостов на отдельные процессы/серверы — текущий VDS справляется; W-26 готовит логическую границу, физическое разделение отложено.

- Мобильное приложение и публичное API — за рамками этапа.
