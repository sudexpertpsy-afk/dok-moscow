# Быстродействие (W-31)

Замеры и ожидания по фронтенду/статике после пакета W-31.

## Что сделано

- **Хэширование статики** (`web/scripts/hash_static.py`): `app.css`, `landing.css`, JS → `name.<sha10>.ext` + `manifest.json`; в Docker вызывается при сборке образа.
- **Jinja `static_url()`** — шаблоны кабинета и лендинга подставляют хэшированные имена; без manifest — исходное имя (dev/тесты).
- **Caddy**: `encode zstd gzip`; hashed CSS/JS — `immutable, max-age=1y`; `samples/*.pdf` — 1 сутки; кабинетный HTML на app — `no-store`.
- **Приложение**: лендинг/`/zakon` — `Cache-Control: public, max-age=300`; кабинет/API — `no-store`; для HTMX — `Vary: HX-Request`.
- **Критический CSS** лендинга — инлайн в `landing/base.html` (навигация/фон выше сгиба).
- **Журнал**: HTMX-подгрузка `/cabinet/journal/rows` по `intersect` (кнопка «Ещё…»).
- Герой лендинга — **SVG** (без растровых hero-изображений → CLS от картинок не возникает; WebP не требуется).

## Как мерить

1. Прод-сборка: `./deploy/deploy.sh` (образ app с `hash_static.py`).
2. Chrome DevTools → Network → Disable cache выкл. → повторный заход на `/` и `/cabinet/`: hashed `/static/*.css|js` должны быть `(disk cache)` / `304`.
3. PageSpeed Insights / Lighthouse mobile:
   - лендинг `https://dok.moscow/` — целевой Performance ≥ 95;
   - `/zakon` — ≥ 90.
4. В среде cloud-агента PageSpeed не гонялся (нет стабильного публичного URL); критерии — для приёмки на VDS после деплоя.

| Зона | До | После |
|------|----|-------|
| Повторная загрузка CSS/JS кабинета | полное скачивание | из кэша (immutable) |
