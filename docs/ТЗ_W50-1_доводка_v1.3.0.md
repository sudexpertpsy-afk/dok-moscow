## 1. Репетиция миграции на копии прод-базы

**Зачем.** `a50bc01` создаёт частичный unique-индекс `invites(lower(email)) WHERE is_active`. Если backfill
`is_active` оставит два активных инвайта на один адрес, `CREATE INDEX` упадёт посреди деплоя.

**Что сделать.**

1. `deploy/migrate_rehearsal.sh <backup.tar.age>` — на базе `restore_drill.sh`: расшифровать бэкап,
   поднять временный `postgres:16` на свободном порту, `pg_restore`, затем из образа приложения
   (тот тег, который собираемся выкладывать) выполнить `alembic upgrade head`, `alembic downgrade -1`,
   `alembic upgrade head`. Любая ошибка — ненулевой код и лог в `data/ops/rehearsal.log`. Контейнер и
   каталог удаляются в `trap`.
2. `deploy.sh --tag X --rehearse` — вызывает п. 1 с последним бэкапом **до** `pull/up`; при неуспехе
   деплой не начинается. Флаг обязателен для релизов с миграциями (проверка: если в образе
   `alembic heads` ≠ `alembic current` прод-базы и `--rehearse` не передан — предупреждение и
   вопрос `y/N`).
3. В самой миграции — предпроверка перед созданием индекса:

```python
dups = conn.execute(text("""
    SELECT lower(email), count(*) FROM invites
    WHERE <условие активности, то же, что в backfill>
    GROUP BY 1 HAVING count(*) > 1""")).fetchall()
if dups:
    raise RuntimeError(f"a50bc01: активные дубли инвайтов, разрешите вручную: {dups}")
```

   Падать с понятным списком лучше, чем с `duplicate key value violates unique constraint`.

**Тест.** Фикстурная БД с двумя активными инвайтами на один адрес → миграция падает с `RuntimeError`
и перечислением; после отзыва одного — проходит; `downgrade` возвращает схему (индекс, `is_active`,
`status`, `is_internal`, `signups` удалены), повторный `upgrade` проходит.

## 2. Легаси-инвайты с уже созданной организацией

На проде есть инвайты старого образца с заполненным `org_id`. По новой схеме организация создаётся при
принятии — для легаси это должно означать **присоединение** к существующей организации, не создание
второй.

- `accept_invite`: если `invite.org_id` не пуст и организация существует — создать пользователя в ней
  (роль из инвайта), инвайт → `accepted`; если организация уже удалена (purge) — инвайт → `expired`,
  пользователю сообщение «приглашение устарело, запросите новое».
- Backfill `status` в миграции для легаси: `accepted` если у организации есть пользователь с этим
  e-mail, `expired` если срок вышел, иначе `active`.

**Тесты.** Легаси-инвайт с `org_id` → принятие даёт одного пользователя в существующей организации,
организаций не прибавилось; легаси-инвайт на удалённую организацию → `expired` и сообщение; новый
инвайт (без `org_id`) → организация появляется только при принятии (уже есть — оставить).

## 3. Purge: сначала список, потом удаление

Guard пройдут организации 7–10, и первый суточный прогон удалит их раньше, чем кто-то посмотрит.

- Настройка `PURGE_MODE = dry | live`, по умолчанию после деплоя — `dry`.
- В `dry`: worker пишет кандидатов в лог и событие `org.purge_candidate {org_id, reason, age_days}`,
  ничего не удаляет. В `live` — как в ТЗ W-50 §B.3.
- Админка → «Организации» → блок «Кандидаты на удаление»: список с причинами по guard, кнопка
  «Удалить» на каждой строке (тот же guard), переключатель режима `dry/live` (только service_admin,
  событие `settings.purge_mode_changed`).
- `/admin/status`: строка «Purge: режим dry, кандидатов N» — жёлтая, пока режим `dry` дольше 7 дней.

**Тесты.** В `dry` организации остаются, событие есть; в `live` удаляются; переключатель пишет событие;
кнопка недоступна для org_admin (IDOR).

## 4. `is_internal`: не seed по именам

Seed по названиям организаций в миграции ненадёжен (переименование, дубликаты). Убрать seed из
миграции; вместо него — `INTERNAL_ORG_IDS` в настройках (список id) применяется **один раз** командой
`manage.py mark_internal` с выводом «помечено: …», а источник правды — переключатель в админке.
Тест: команда идемпотентна, несуществующий id — предупреждение, не ошибка.

## 5. Микрофикс маркеров из v1.2.3

**5.1. `mail_auth_ok.json` привязан к домену.** При «Подтвердить» в маркер пишется `from_domain` (из
`SMTP_FROM` на момент подтверждения) и `confirmed_at`. Строка «Почта» в `/admin/status` зелёная только
если одновременно: `from_domain == "dok.moscow"`, текущий домен `SMTP_FROM` равен домену маркера,
маркер моложе 180 дней. Иначе — красная с причиной («подтверждено для gmail.com», «домен изменился»,
«маркера нет»). Тест на все четыре состояния.

**5.2. `sha` в `deploy.log`.** В GitHub Actions при сборке образа — label
`org.opencontainers.image.revision=${{ github.sha }}` (и `org.opencontainers.image.version=<тег>`).
`deploy.sh` берёт SHA командой
`docker image inspect "$IMAGE:$TAG" --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'`;
если пусто — из `/healthz` (поле `sha`, добавить, если его там нет); `unknown` — только если оба
источника пусты, и тогда предупреждение в лог. Индикатор дрейфа сравнивает этот SHA с `origin/main`.
