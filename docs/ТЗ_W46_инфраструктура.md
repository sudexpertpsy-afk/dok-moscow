# W-46. Инфраструктурная гигиена: разделение кода и данных, воспроизводимый деплой

Основание: docs/структура_и_сервер.md (снимок 2026-09-07). Регламент:
ветка = сессия Cursor, тесты обязательны, изменения инфраструктуры —
с планом отката и проверкой restore.

## 0. Анализ: что документ фиксирует как «особенности», а на деле — риски

Документ описывает семь ловушек. Шесть из них — один и тот же корень:
**на сервере смешаны код (git working tree) и рантайм-данные**, а
деплой идёт не через git, а мимо него.

| № | Что описано в карте | Почему это риск | Уже проявлялось |
|---|---|---|---|
| Р-1 | Шаблоны RW-bind внутри git-дерева; админка пишет в `/srv/dok/core/Шаблоны` | `git pull/stash/checkout` может затереть правки админки; dirty tree блокирует деплой | ДА — инцидент 02.08: `stash pop` удалил DOCX-шаблоны |
| Р-2 | `/srv/dok/files` на хосте ≠ volume `dok_files`; реальные данные в `/var/lib/docker/volumes/…` | Любой скрипт, глядящий на host-путь, видит пустоту | ДА — G-01: слепой маркер бэкапа |
| Р-3 | Хотфиксы через `scp` + build; «файлы на диске новее git log»; прод на ветке `cursor/*` (e603ffa) | Прод невоспроизводим: нельзя откатиться, нельзя сказать, какой код работает; аудит сверял руками | ДА — аудит №2 начинался со сверки SHA |
| Р-4 | Диск ~50% из 30 ГБ (аудит 02.08 — 29%, 04.08 — 32%) | +20 п.п. за месяц → порог 85% через ~2 месяца; вероятно, слои образов от частых `--no-cache` | тренд |
| Р-5 | Состояние мастера — JSON-файлы в `FILES_ROOT/_wizard/` | Нет TTL и очистки; мусор растёт; не запись БД — не под транзакцией и не в отчётах | латентно |
| Р-6 | DaData-кэш и rate-limit «на пользователя» — in-process, а uvicorn — 2 воркера | Лимиты «протекают» ×2, кэш дублирует запросы; при 4 воркерах — ×4 | латентно |
| Р-7 | Три копии шаблонов: desktop `Шаблоны/`, repo `core/Шаблоны`, прод-bind | Инвариант «формат нельзя ломать без миграции всех шаблонов» — тройная стоимость любой правки | постоянно |

Плюс: манифесты есть лишь у «части новых шаблонов» (~40 файлов), репо
до сих пор `desktop-tutorial`, `rsync` на сервере нет.

Вывод: не латать по одному — провести одно структурное изменение
(разделить код и данные + деплой образом по тегу), от которого Р-1…Р-3
исчезают по построению, а остальное закрыть точечно.

## 1. Разделение кода и данных на сервере (ядро пакета)

Целевая схема:

```
/srv/dok/app/          # ТОЛЬКО git checkout (или вообще без checkout —
                       # см. §2), read-only для рантайма
/srv/dok/data/         # ТОЛЬКО данные, вне git, единый путь хост==контейнер
├── files/             # FILES_ROOT (bind вместо named volume)
│   └── {org_id}/…
├── templates/         # рабочий каталог шаблонов (TEMPLATES_DIR)
│   ├── system/        # системные, синхронизируются деплоем из репо
│   ├── overrides/     # правки админки поверх системных
│   └── .deleted_templates.json
├── wizard/            # (временно, до §4) сессии мастера
├── ops/               # backup_ok и др. маркеры
└── legal/
/srv/dok/deploy/.env   # секреты (как сейчас)
/var/backups/dok/      # бэкапы (как сейчас)
```

Задачи:
1. **FILES_ROOT → bind-mount** `/srv/dok/data/files` в контейнер по
   ТОМУ ЖЕ пути. Миграция: `docker run --rm -v dok_files:/from -v
   /srv/dok/data/files:/to alpine cp -a /from/. /to/` при остановленном
   app/worker; проверка counts файлов и хэшей выборки; старый volume
   оставить 7 дней, затем удалить. backup.sh, ops-agent, маркеры —
   на новый путь. Р-2 и G-01-класс исчезают: host-путь == данные.
2. **Шаблоны как данные, репо — как seed.** `TEMPLATES_DIR=
   /srv/dok/data/templates`; ядро читает system + overrides (override
   с тем же именем перекрывает системный). deploy.sh синхронизирует
   `core/Шаблоны` репо → `system/` (rsync -a --delete по системному
   списку; overrides не трогает). Админка пишет ТОЛЬКО в `overrides/`
   и tombstone. Кнопка админки «Экспорт правок шаблонов (zip)» — чтобы
   владелец мог внести override в репо осознанно. Р-1 исчезает: git не
   касается того, что редактирует админка.
3. Установить `rsync` на VDS (apt); deploy.sh — идемпотентный,
   с `set -euo pipefail`, шагами и логом в `/srv/dok/data/ops/deploy.log`.
4. Ядро `core/` больше не bind из git-дерева: код ядра — часть образа
   (COPY core), как и web/app. Шаблоны — из data. Тогда «правка .py на
   хосте» перестаёт быть отдельным путём в прод.

Критерии: `git status` на сервере всегда чист; удаление и повторный
клон `/srv/dok/app` не теряют ни одного файла данных; restore drill из
бэкапа поднимает data-каталог целиком.

## 2. Воспроизводимый деплой: образ по тегу, без scp

1. **CI-сборка**: GitHub Actions на push в `main` и на тег `v*` —
   build образа `web` (multi-stage, с хэшированием статики внутри) →
   push в GHCR как `ghcr.io/<owner>/dok-app:<sha>` и `:vX.Y.Z`.
   В образ зашивается `APP_VERSION=<sha>`/тег.
2. **deploy.sh на сервере** = `docker compose pull` конкретного тега +
   `alembic upgrade` + `up -d` + smoke (`/healthz`, `/admin/status`
   через ops-agent) + `docker image prune -af --filter until=168h`.
   Никакой сборки на VDS (снимает нагрузку с 2 vCPU и убирает
   `--no-cache`-мусор — Р-4).
3. **Запрет scp-хотфиксов** — организационно и технически: рабочее
   дерево на сервере не нужно (§1.4), править нечего; хотфикс =
   коммит в main → тег → deploy. Время цикла CI ≤ 5 мин — это
   быстрее, чем scp + build на сервере.
4. **Контроль дрейфа**: `/admin/status` показывает работающий
   `APP_VERSION` и сравнивает с последним тегом `origin/main` (через
   GitHub API или файл-маркер CI); расхождение > 24 ч или прод не на
   теге — жёлтый индикатор + письмо. Прод НИКОГДА не на ветке
   `cursor/*`.
5. Откат: `deploy.sh --rollback` = предыдущий тег из deploy.log +
   `alembic downgrade` при необходимости (миграции обязаны иметь
   рабочий downgrade — тест в CI).

Критерии: деплой чистого VDS из тега — ≤ 15 мин по docs; `git log` на
сервере отсутствует как источник правды; версия в /admin/status
совпадает с тегом релиза.

## 3. Диск: остановить рост

1. Разобрать структуру занятого: `docker system df -v`, размер
   `/var/backups/dok`, `pgdata`, `files`, journald. Зафиксировать
   в docs.
2. Ежедневный `docker image prune -af --filter until=168h` +
   `builder prune` (после §2 сборок на сервере нет, но старые слои
   вычистить сейчас).
3. Проверить ротацию бэкапов (30 суточных + 12 месячных) фактически
   по `ls`, не по замыслу; journald `SystemMaxUse=500M`.
4. Порог алерта диска 85% → 75% (W-32); тренд «+X ГБ/нед» в
   /admin/status.

Критерий: после чистки ≤ 35%; недельный рост < 2%.

## 4. Состояние мастера комплекта — в БД

Таблица `wizard_sessions(sid, org_id, user_id, state JSONB,
updated_at, expires_at)`; чтение/запись через
`package_wizard_store` тем же интерфейсом (файловый бэкенд удаляется
после миграции). Worker чистит истёкшие (TTL 24 ч). Плюс: черновик
переживает рестарт, виден в отчётах, под бэкапом БД, не растит FS.
Тест: 2 воркера uvicorn пишут/читают одну сессию согласованно.

## 5. Кэш и лимиты — общие для воркеров

1. DaData: суточный лимит на org и rate-limit на пользователя —
   счётчики в PostgreSQL (таблица `rate_counters(key, window,
   count)`, UPSERT), не в памяти процесса. Тест: лимит N соблюдается
   при 2+ воркерах (запросы вразнобой).
2. Кэш ответов DaData — допустимо оставить in-process с TTL ≤ 10 мин
   ИЛИ вынести в таблицу `dadata_cache` (экономия платных запросов
   при повторных ИНН по всем воркерам — рекомендуется).
3. Ревизия всех остальных in-process состояний (rate limits входа/2FA/
   webhook-счётчик алертов) — те же правила.

## 6. Шаблоны: единый источник и полнота метаданных

1. Манифест `*.manifest.yaml` — у КАЖДОГО системного шаблона (~40);
   тест «шаблон без манифеста = падение CI». Черновики манифестов —
   генератором W-11, подписи вычитывает владелец.
2. `contracts_registry.json` валидируется тестом против файлов
   (каждый ключ → существующий DOCX; каждый DOCX пакета → ключ).
3. Desktop DocFiller: решение владельца — (а) заморозить как
   legacy (рекомендуется: веб покрывает сценарии) или (б) перевести
   на чтение `core/Шаблоны` из клона репо (настройка пути) и убрать
   локальную копию `Шаблоны/`. В любом случае — исключить третью
   копию: «источник правды шаблонов = репо, рабочая копия = прод
   data/templates, точка».

## 8. Порядок, риски, приёмка

Порядок (каждый шаг — отдельный деплой с откатом):
1) §3 чистка диска (без риска) → 2) §1.1 FILES_ROOT bind + миграция
volume (окно техработ 15 мин, бэкап до/после) → 3) §1.2 шаблоны в
data + deploy-sync → 4) §2 CI-образ + новый deploy.sh (первый релиз
тегом с текущего состояния main, сверив с прод-файлами!) →
5) §4, §5 → 6) §6, §7.

Особый риск шага 4: прод сейчас содержит scp-правки, которых может не
быть в git. ПЕРЕД переходом на образ по тегу — снять diff «файлы в
контейнере vs origin/main» (docker cp app dir → diff -r) и внести
недостающее в репо коммитом. Иначе первый «чистый» деплой откатит
живые хотфиксы.

Критерии приёмки пакета:
- [ ] `git status` на сервере чист / working tree не используется рантаймом
- [ ] host-путь данных == путь в контейнере; backup/restore drill зелёный
- [ ] прод на теге релиза, версия видна в /admin/status, дрейф-алерт работает
- [ ] диск ≤ 35%, prune в расписании
- [ ] wizard в БД, TTL-очистка работает
- [ ] лимиты DaData соблюдаются при 2 воркерах (тест)
- [ ] манифест у 100% системных шаблонов; реестр валиден тестом
- [ ] решение по desktop принято и зафиксировано в docs

Оценка: §3 — 0,5 дн.; §1 — 2–3 дн.; §2 — 2–3 дн.; §4–5 — 2 дн.;
§6–7 — 1–2 дн. Итого 8–11 дней; выигрыш — исчезновение целого класса
инцидентов (Р-1, Р-2, Р-3), которые уже дважды случались.
