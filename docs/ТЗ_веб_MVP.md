# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

на разработку веб-сервиса «Док.Москва» (dok.moscow)

MVP на базе ядра приложения «Шаблонер» · реализация в Cursor (платный тариф)

ООО «УСЭ» · 31 июля 2026 г. · версия 1.0


## 1. Общие положения

### 1.1. Цель

Создать веб-версию «Шаблонера» — сервис dok.moscow: личный кабинет экспертной организации с генерацией документов, картотекой контрагентов, подсказками из открытых баз (ЕГРЮЛ, ФИАС, банки через DaData) и выдачей Word/PDF. Настоящее ТЗ покрывает MVP (закрытая бета) и развёртывание на VDS Hostland; биллинг и публичная регистрация — отдельным ТЗ после подтверждения спроса.

### 1.2. Исходные активы

- Репозиторий DocFiller (архив Шаблонер_полная_версия_2026-07-31): бизнес-ядро без Tk-зависимостей — filler.py, filters.py, master.py, packages.py, validators.py, counters.py, config.py, db.py, journal.py, labels.py, registry.py, paths.py, errors.py, backup.py; 26 шаблонов DOCX; тесты pytest (~20 файлов).

- Домен dok.moscow (текущий сайт подлежит замене), хостинг Hostland: заказать VDS 2 vCPU / 4 ГБ RAM / 40 ГБ NVMe, Ubuntu 24.04 LTS, root по SSH.

- Ключ API DaData (бесплатный тариф, до 10 000 запросов/сутки).

### 1.3. Требования и ограничения

- **Стек:** Python 3.12, FastAPI + Jinja2-шаблоны страниц + HTMX (серверный рендеринг, без SPA-фреймворка — минимум сущностей для сопровождения одним человеком), PostgreSQL 16, SQLAlchemy 2 + Alembic, Docker Compose, Caddy (автоматический HTTPS), Gotenberg (DOCX→PDF).

- **Без ИИ-функций в продукте.** ИИ — только инструмент разработки (Cursor).

- **Мультитенантность с первого дня:** каждая запись данных принадлежит организации (org_id); пользователь видит только свою организацию. В бете организации создаются администратором (инвайты).

- **Русский язык** интерфейса, кода-комментариев, коммитов. Совместимость шаблонов: формат переменных и фильтров Шаблонера не меняется — шаблоны DOCX используются как есть.

- **Данные в РФ:** все данные и бэкапы — на VDS Hostland и в российском объектном хранилище (или на компьютере заказчика).

## 2. Архитектура

> Браузер ──HTTPS──► Caddy ──► FastAPI (app)
>
> │ docfiller_core (ядро Шаблонера)
>
> │ DaData API (подсказки: ИНН/адрес/БИК)
>
> ├─► PostgreSQL 16 (данные организаций)
>
> ├─► Gotenberg (DOCX → PDF)
>
> └─► /srv/dok/files (готовые документы)
>
> Docker Compose: caddy · app · postgres · gotenberg
>
> Бэкап: pg_dump + files → архив → внешнее хранилище (ежедневно, cron)

Монорепозиторий dok-moscow: пакет core/ (перенесённое ядро docfiller без Tk), web/ (FastAPI-приложение), deploy/ (compose, Caddyfile, скрипты), docs/ (настоящее ТЗ в Markdown, регламенты). Настольный Шаблонер продолжает жить в своём репозитории; ядро синхронизируется копированием пакета core (в перспективе — общий пакет).

## 3. Рабочие пакеты

Создать .cursor/rules/project.mdc по Приложению В.

Критерии приёмки: pytest ядра зелёный; fill_template генерирует документ из шаблона Шаблонера в чистом окружении Linux (важно: petrovich, num2words, docxtpl работают без macOS-специфики).

Перенеси в core/docfiller_core модули ядра из @DocFiller/docfiller (filler, filters, master, packages, validators, counters, journal, labels, db, errors — без tkinter-модулей) вместе с тестами. Отвяжи ядро от macOS-путей: все пути и настройки организации передаются параметрами. Убедись, что pytest проходит на Linux. Коммит «W-00: перенос ядра Шаблонера».*

### W-01. Каркас веб-приложения и аутентификация

Задачи: FastAPI-приложение с серверными страницами (Jinja2 + HTMX); базовый макет кабинета (навигация: Документы, Комплект, Контрагенты, Журнал, Настройки); аутентификация по e-mail и паролю (сессии в подписанных cookie, bcrypt), приглашения: администратор создаёт организацию и отправляет ссылку-инвайт; роли: администратор сервиса / пользователь организации. Защита: CSRF, rate limiting на вход, security-заголовки.

Критерии приёмки: пользователь по инвайту создаёт пароль и попадает в пустой кабинет своей организации; чужие URL недоступны (проверка org_id в каждом запросе); OWASP-базовые проверки пройдены.

### W-02. Схема данных PostgreSQL

Задачи: модели SQLAlchemy + миграции Alembic по Приложению А: organizations, users, counterparties (контрагенты), contracts, documents, counters, events — всё с org_id и индексами. Настройки организации (реквизиты, банк, подписанты, прайс, склонения) — JSONB-поле организации, совместимое по структуре с настройки.yaml Шаблонера (ядро получает их как словарь).

Критерии приёмки: alembic upgrade head на чистой базе; фикстуры двух организаций; тест изоляции — данные одной организации не видны другой ни в одном запросе.

### W-03. Генерация документов и PDF

Задачи: страница «Отдельный документ»: выбор шаблона из каталога (группы Шаблонера), форма полей (генерация формы — из переменных шаблона, как в Шаблонере), предпросмотр, генерация DOCX ядром docfiller_core; сохранение файла в files/{org}/{ГГГГ-ММ}/, запись в documents; скачивание DOCX; конвертация в PDF через Gotenberg и «Комплект одним PDF» (pypdf). Счётчики номеров — из таблицы counters с блокировкой на уровне БД (никаких гонок при двух пользователях).

Критерии приёмки: все 26 шаблонов генерируются в вебе с результатом, идентичным настольному Шаблонеру (сверка на эталонных контекстах из тестов); PDF читаем; номера не дублируются при параллельных запросах (тест).

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-03: эндпойнты и страницы генерации документов на базе core/docfiller_core.fill_template. Форма строится из collect_variables шаблона; контекст дополняется настройками организации (JSONB → словарь «настройки»). Файлы — в files/{org_id}/{ГГГГ-ММ}/, метаданные — в documents. Конвертация PDF через Gotenberg (HTTP), объединение комплекта pypdf. Счётчики — SELECT ... FOR UPDATE. Тесты: идентичность DOCX эталонам Шаблонера, параллельная нумерация. Прогони pytest.*

### W-04. Мастер комплектов

Задачи: перенести поток master.py в веб: шаг 1 — контрагент (тип ФЛ/ЮЛ/эксперт + выбор из картотеки или новый), шаг 2 — договор и сопутствующие документы (логика packages.py, SELF_CONTAINED), шаг 3 — объединённые поля комплекта, шаг 4 — генерация всех документов с итоговой страницей (скачать по одному / комплект одним PDF / все в ZIP).

Критерии приёмки: комплект ФЛ (договор+счёт+акт+ПКО), ЮЛ и ГПД собираются как в настольной версии; «Повторить» из журнала предзаполняет мастер.

### W-05. Картотека контрагентов и подсказки DaData

Задачи: CRUD контрагентов (ФЛ/ЮЛ/эксперт) с валидацией validators.py; серверное проксирование DaData (ключ хранится только на сервере, лимит на организацию — защита от исчерпания квоты): подсказки организаций по ИНН/названию (автозаполнение карточки ЮЛ: наименование, ОГРН, КПП, адрес, руководитель), адресов по ФИАС, банков по БИК. История документов в карточке контрагента; маскирование паспортных данных в списках.

Критерии приёмки: ввод ИНН заполняет карточку ЮЛ за один клик; отключение DaData (нет сети/ключа) деградирует мягко — ручной ввод со всеми валидациями работает.

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-05: модуль web/dadata.py — серверный прокси к API DaData (suggest/party по ИНН, suggest/address, suggest/bank по БИК) с кэшированием повторных запросов и суточным лимитом на организацию; ключ — из переменной окружения. На страницах контрагента — HTMX-подсказки: выбор из выпадающего списка заполняет поля формы. Валидации из core (ИНН/ОГРН/БИК/счёт) сохраняются для ручного ввода. Тесты с замоканным DaData. Прогони pytest.*

### W-06. Журнал, поиск, настройки организации

Задачи: журнал документов с фильтрами (период, шаблон, контрагент) и постраничным выводом; сквозной поиск (контрагенты, договоры, документы); страницы настроек организации — формы «Реквизиты», «Банк», «Подписанты», «Прайс» (структура как в settings-формах Шаблонера) с валидацией; управление счётчиками (просмотр следующего номера, корректировка с подтверждением).

Критерии приёмки: поиск «Иванов» находит контрагента и его документы; изменение реквизитов сразу отражается в новых документах.

### W-07. Развёртывание на VDS Hostland

Задачи: deploy/compose.yml (caddy, app, postgres, gotenberg) по Приложению Б; Caddyfile для dok.moscow и app.dok.moscow с автоматическим Let’s Encrypt; deploy/deploy.sh — обновление одной командой (git pull, build, migrate, restart); deploy/backup.sh — ночной pg_dump + архив файлов + выгрузка во внешнее хранилище, ротация 30/12; восстановление restore.sh; фаервол (ufw: 22/80/443), fail2ban, автообновления безопасности; мониторинг Uptime Kuma (или UptimeRobot) с уведомлением на телефон. Документ docs/эксплуатация.md: установка с нуля за час, регламент обновления, действия при аварии.

Критерии приёмки: развёртывание на чистом VDS по документации — до 1 часа; restore.sh на втором чистом VDS поднимает рабочую копию из бэкапа; HTTPS-рейтинг A (ssllabs).

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-07 по Приложению Б: compose.yml, Caddyfile, deploy.sh, backup.sh, restore.sh, настройка ufw и fail2ban (скрипт server_init.sh для чистого Ubuntu 24.04). Напиши docs/эксплуатация.md: пошаговая установка на VDS Hostland, обновление, бэкап/восстановление, чек-лист аварии. Все скрипты идемпотентны, сообщения на русском.*

### W-08. Лендинг dok.moscow

Задачи: главная страница (отдаётся тем же приложением): позиционирование «кабинет экспертной организации», примеры документов (обезличенные PDF), тарифы (как в концепции, с пометкой «бета — по приглашениям»), форма заявки на ранний доступ (e-mail + профиль деятельности) с записью в базу и уведомлением администратору; страницы «Политика обработки ПДн» и «Контакты»; базовое SEO (мета-теги, sitemap, микроразметка), счётчик Яндекс.Метрики.

Критерии приёмки: лендинг открывается на dok.moscow по HTTPS, заявки сохраняются и приходят на почту администратора; PageSpeed ≥ 90 (страница статическая).

### W-09. Безопасность и ПДн

Задачи: аудит по чек-листу OWASP ASVS L1 силами Cursor (промпт-ревизия); шифрование бэкапов (age/gpg); политика паролей и восстановление по e-mail; журнал входов (events); автоматическое удаление файлов документов по настройке организации (например, старше 3 лет); проект уведомления в Роскомнадзор и текст политики ПДн (юридическую вычитку заказчик делает отдельно).

Критерии приёмки: чек-лист аудита закрыт или зафиксирован в docs/безопасность.md с обоснованием; бэкапы нечитаемы без ключа.

## 4. Что сознательно не входит в MVP

- Биллинг и публичная регистрация (этап «Версия 1.0» — отдельное ТЗ: ЮKassa, тарифные лимиты, личные счета).

- Статусы/сроки договоров и панель «Требуют внимания» (переносится из ТЗ этапов 4–6 после беты).

- Загрузка пользовательских шаблонов (риски безопасности Jinja2-шаблонов от чужих пользователей требуют песочницы — версия 1.5).

- Мобильное приложение, API, командные роли внутри организации.

## 5. Регламент работы в Cursor

- Один пакет W-NN = одна ветка = одна сессия агента; правила проекта — Приложение В; ТЗ лежит в docs/ТЗ_веб_MVP.md, агент ссылается на него через @.

- Тесты обязательны (pytest + httpx для эндпойнтов); перед слиянием — прогон полного набора и ручной smoke-тест по чек-листу раздела 6.

- Секреты (ключ DaData, пароли БД) — только в .env на сервере, в репозиторий не попадают (.env.example с плейсхолдерами).

- Эталоны совместимости: DOCX-файлы, сгенерированные настольным Шаблонером на тестовых контекстах, хранятся в tests/etalon/ — веб-версия обязана выдавать идентичное содержимое.

## 6. Чек-лист приёмки MVP

- Вход по инвайту; заполнение реквизитов организации; генерация комплекта ФЛ; сверка содержимого договора, счёта, акта, ПКО с настольной версией.

- Контрагент-ЮЛ по ИНН через DaData; адрес по ФИАС; комплект ЮЛ; ГПД с экспертом + согласие ПДн.

- Комплект одним PDF; повтор из журнала; поиск; корректность следующих номеров после серии генераций.

- Изоляция двух организаций; недоступность чужих файлов по прямым URL.

- Обновление приложения deploy.sh без потери сессий данных; восстановление из ночного бэкапа на чистом VDS.

- Лендинг: заявка с телефона; скорость; ссылки на политику ПДн.
