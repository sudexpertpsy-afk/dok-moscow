# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

Биллинг сервиса «Док.Москва»: оплата картой через Т-Банк,

настройки платёжной системы и учёт платежей в панели администратора

Этап «Версия 1.0» · реализация в Cursor · рабочие пакеты W-10…W-15

ООО «УСЭ» · 1 августа 2026 г. · версия 1.0


## 1. Цель и рамки

Добавить в развёрнутый на dok.moscow сервис приём оплаты банковской картой через интернет-эквайринг Т-Банка (Т-Касса), страницу «Тариф и оплата» в кабинете организации, раздел настройки платёжной системы и полный учёт поступивших платежей в панели администратора. После этого этапа сервис переходит из закрытой беты в публичный платный режим.

Основание: концепция сервиса (тарифы «Гость» 0 ₽, «Специалист» 990 ₽/мес или 9 900 ₽/год, «Организация» 2 490 ₽/мес или 24 900 ₽/год) и ТЗ на веб-MVP (раздел «Что сознательно не входит в MVP»). Работы ведутся в Cursor по регламенту прежних ТЗ: один пакет — одна ветка — одна сессия, тесты обязательны, ТЗ лежит в docs/ТЗ_биллинг.md.

### 1.1. Предварительные условия (выполняет владелец до начала работ)

- **Договор эквайринга.** Заключить с Т-Банком договор на интернет-эквайринг (продукт «Т-Касса») на ООО «УСЭ»; в личном кабинете Т-Бизнеса получить ДВА терминала: тестовый и боевой (TerminalKey + пароль каждого).

- **Онлайн-касса 54-ФЗ.** Подключить облачную кассу через Т-Банк (чеки формирует банк по данным Receipt из запроса) — рекомендуемый вариант; либо указать собственную кассу. Налогообложение позиций — УСН, без НДС (сверить с бухгалтером).

- **URL уведомлений.** В настройках терминала указать адрес вебхука: https://dok.moscow/billing/webhook.

- **Оферта.** Разместить публичную оферту и реквизиты ООО «УСЭ» на сайте (черновики юридических текстов — отдельно, юридическая вычитка на стороне владельца).

### 1.2. Требования к интеграции

- **Актуальность API.** Перед реализацией агент Cursor обязан сверить методы и поля с действующей документацией Т-Банка (developer.tbank.ru, раздел интернет-эквайринга). Ориентировочная схема (проверить!): POST Init → PaymentURL для редиректа; вебхук Notification со статусами; GetState для сверки; Charge по RebillId для автосписаний; подпись Token = SHA-256 от отсортированных параметров с паролем терминала.

- **Секреты.** Пароль терминала хранится в базе в зашифрованном виде (Fernet, ключ выводится из SECRET_KEY приложения); в логи и отчёты не попадает. TerminalKey — не секрет, но тоже не логируется без нужды.

- **Идемпотентность.** Повторная доставка одного и того же вебхука (обычное поведение банков) не должна создавать дублей платежей или повторных продлений подписки.

- **Никаких карточных данных на нашей стороне.** Ввод карты — только на платёжной странице Т-Банка (редирект/виджет); сервис не принимает и не хранит PAN/CVC ни в какой форме.

## 2. Рабочие пакеты

### W-10. Модель данных биллинга

Задачи: таблицы (Alembic-миграции, все с org_id где применимо):

> tariffs — справочник: код (гость/специалист/организация), название,
>
> цена_месяц, цена_год, лимит_документов_мес, лимит_пользователей,
>
> водяной_знак BOOL, активен
>
> subscriptions— org_id, тариф, период (месяц/год), начало, окончание,
>
> статус (trial/active/expired/cancelled), автопродление BOOL,
>
> customer_key, rebill_id NULL
>
> payments — id (UUID, он же OrderId для банка), org_id, subscription_id,
>
> сумма_коп, назначение, статус (created/authorized/confirmed/
>
> rejected/refunded/partial_refund), tbank_payment_id,
>
> источник (карта/вручную), чек_статус, error_code,
>
> raw_события JSONB\[\], создан, обновлён
>
> payment_settings — singleton: terminal_key, password_encrypted, режим
>
> (тест/бой), рекурренты BOOL, налогообложение, ставка_ндс,
>
> email_для_чеков_по_умолчанию, обновлён, кем

Бесплатный тариф «Гость» и бета-организации моделируются подписками со статусом trial без платежей. У существующих организаций беты при миграции создаётся подписка «Организация» (чтобы на бете хватало слотов пользователей), период до `BETA_TRIAL_UNTIL`, с пометкой «бета».

Критерии приёмки: миграции применяются на боевой схеме без потери данных; тесты моделей и переходов статусов подписки; лимиты тарифов читаются из базы, а не из кода.

### W-11. Интеграция с Т-Кассой

Задачи: модуль web/billing/tbank.py:

- **Init:** создание платежа (сумма, OrderId=payments.id, Description, DATA.Email, Receipt для чека, NotificationURL, SuccessURL/FailURL на страницы кабинета); при включённых рекуррентах и согласии пользователя — Recurrent=Y + CustomerKey. Ответ: PaymentId, PaymentURL → редирект пользователя.

- **Подпись Token:** генерация по актуальному алгоритму документации (SHA-256, сортировка полей, Password); одна функция + тесты на эталонных примерах из документации.

- **Вебхук POST /billing/webhook:** проверка Token; поиск платежа по OrderId; запись события в raw_события; обновление статуса; при CONFIRMED — активация/продление подписки (транзакционно, идемпотентно); сохранение RebillId при первом рекуррентном платеже; ответ строкой OK.

- **Сверка GetState:** фоновая задача каждые 30 минут для платежей в промежуточных статусах старше 15 минут; ручная кнопка «Сверить» в админке.

- **Автопродление:** ежедневная задача: за 3 дня до окончания подписки с автопродлением и RebillId — Init+Charge; при неудаче повтор через сутки, максимум 3 попытки, затем письмо владельцу организации и статус expired по сроку.

Критерии приёмки: полный цикл на тестовом терминале — оплата, отказ, повторный вебхук без дублей, возврат из ЛК банка отражается как refunded; юнит-тесты с эмулятором вебхуков (fixtures реальных форматов уведомлений).

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-11 по docs/ТЗ_биллинг.md. Сначала изучи актуальную документацию интернет-эквайринга Т-Банка (developer.tbank.ru): методы Init/GetState/Charge, формат Notification, алгоритм Token, поля Receipt (54-ФЗ). Затем: модуль web/billing/tbank.py (httpx), вебхук /billing/webhook с проверкой подписи и идемпотентностью, фоновые задачи сверки и автопродления. Секрет терминала — из payment_settings (расшифровка Fernet). Тесты: подпись на эталонах, вебхук-эмулятор (успех/отказ/дубль), активация подписки. Прогони pytest.*

### W-12. Кабинет организации: «Тариф и оплата»

- Страница: текущий тариф, срок действия, использование лимитов (документов за месяц); кнопки «Оплатить месяц» / «Оплатить год (−2 месяца)» с выбором тарифа; чекбокс «Продлевать автоматически» (виден только при включённых рекуррентах в настройках).

- История платежей организации: дата, сумма, статус, ссылка «Чек» (из уведомления банка о чеке).

- Страницы возврата SuccessURL/FailURL: понятный итог + автоматическое обновление статуса (poll GetState, если вебхук ещё не пришёл).

- Ограничение по тарифу: middleware лимитов — «Гость»: 3 документа/мес и водяной знак на PDF; «Специалист»: 1 пользователь; «Организация»: до 5 пользователей и свои шаблоны. Мягкая деградация при истечении подписки: просмотр и скачивание доступны, генерация новых документов — после оплаты (данные никогда не блокируются).

Критерии приёмки: сценарий «истекла подписка → оплата → лимиты сняты» проходит без участия администратора; водяной знак появляется только у «Гостя».

### W-13. Панель администратора: платёжная система и учёт платежей

Раздел «Платёжная система» (только для роли администратора сервиса):

- Форма: TerminalKey, пароль терминала (ввод скрыт, хранение шифрованно, при просмотре — только «•••• задан»), режим Тест/Бой, включить рекуррентные платежи, система налогообложения и ставка НДС для чеков.

- Кнопка «Проверить подключение»: тестовый Init на 10 ₽ с немедленной отменой (Cancel) — результат на экране; в боевом режиме кнопка предупреждает.

- Журнал изменений настроек в events (кто и когда менял, без значений секретов).

Раздел «Платежи» — учёт всех поступлений через сайт:

- Таблица: дата, организация, тариф/период, сумма, источник (карта/вручную), статус, PaymentId банка, чек; фильтры по периоду/статусу/организации; поиск по сумме и PaymentId.

- Карточка платежа: полная хронология событий вебхуков (raw), кнопки «Сверить (GetState)» и «Отметить возврат».

- Сводка сверху: за текущий месяц — поступило ₽, платежей, новых подписок, активных подписок всего, MRR; за прошлый месяц для сравнения.

- Экспорт в Excel отфильтрованного списка (для бухгалтерии): дата, плательщик (организация, ИНН из карточки), сумма, назначение, PaymentId, статус чека.

- Ручная операция «Продлить подписку вручную» (оплата пришла по счёту на р/с, вне сайта): создаёт payment с источником «вручную» и продлевает подписку; обязательное поле «основание» (номер п/п).

Критерии приёмки: любой поступивший через сайт платёж виден в учёте не позднее прихода вебхука; суммы сводки сходятся с суммой строк (тест); экспорт открывается в Excel с русскими заголовками.

> **Промпт для Cursor (режим Agent):**
>
> *Реализуй W-13 по docs/ТЗ_биллинг.md: разделы админ-панели «Платёжная система» (форма настроек с шифрованием пароля терминала Fernet-ключом из SECRET_KEY, кнопка проверки подключения через тестовый Init+Cancel, журнал изменений в events) и «Платежи» (таблица с фильтрами и поиском, карточка платежа с raw-событиями, GetState-сверка, ручное продление с основанием, сводка месяца с MRR, экспорт в Excel через openpyxl). Доступ — только роли администратора сервиса, все действия журналируются. Тесты: права доступа, сходимость сводки, идемпотентность ручного продления. Прогони pytest.*

### W-14. Чеки 54-ФЗ, письма и юридические страницы

- Receipt в Init: позиция «Подписка Док.Москва, тариф …, период …», количество 1, цена=сумма, признак «услуга», полная предоплата; email плательщика (из профиля организации, с возможностью указать другой на странице оплаты).

- Обработка уведомлений о чеке (если терминал их присылает): сохранение ссылки/статуса чека в payments.

- Письма (SMTP из настроек): успешная оплата (+ссылка на чек), скорое окончание подписки (за 7 и за 1 день, если автопродление выключено), неудачное автосписание, подтверждение ручного продления.

- Страницы: оферта, политика ПДн (обновить: добавлен оператор платежей), реквизиты, тарифы. Тексты — черновики, финальную вычитку делает владелец.

Критерии приёмки: в тестовой оплате чек формируется с правильной позицией и СНО; письма приходят и корректно выглядят в почте.

### W-15. Тестирование, приёмка, переключение в бой

- Чек-лист на тестовом терминале: успешная оплата месяц/год обоих платных тарифов; отказ (недостаточно средств); двойная доставка вебхука; возврат; автосписание (эмуляция даты); смена тарифа в середине периода (доплата с перерасчётом дней — реализовать простейшую схему: новый период начинается сразу, остаток дней конвертируется в дни нового тарифа по стоимости); истечение без оплаты.

- Нагрузочный мини-тест вебхука (100 подряд) — без дублей и ошибок.

- Переключение: в админке режим «Бой», боевой TerminalKey; первая реальная оплата на 10 ₽ владельцем с возвратом; после успеха — публикация тарифов на лендинге.

Критерии приёмки: весь чек-лист зелёный, зафиксирован в docs/приёмка_биллинг.md с датами и результатами.

## 4. Безопасность и учётная дисциплина

- Вебхук доступен без аутентификации (так работает банк), но проверяет подпись Token и принимает только известные OrderId; на эндпойнт — rate limit и логирование всех отклонённых запросов.

- Все денежные значения — в копейках, целыми числами; никаких float в расчётах.

- Продление подписки и запись платежа — в одной транзакции БД; сбой после ответа банка устраняется сверкой GetState.

- Экспортные файлы для бухгалтерии не содержат ничего лишнего из ПДн (только реквизиты плательщика-организации).

- Резервные копии (backup.sh) уже включают новые таблицы автоматически (pg_dump всей базы) — проверить в W-15 восстановлением на тестовой базе.
